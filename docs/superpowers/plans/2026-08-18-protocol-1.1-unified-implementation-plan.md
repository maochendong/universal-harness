# Universal Harness Protocol 1.1 统一实施计划

> 状态：仓库内能力已实施并通过本地证据审计；跨平台发布证据待补
> 主干设计：Slim Profiles 与 Capability Kernel
> 嵌入设计：Managed PRD Capture、DesignSet 生命周期、可证明 TDD、模型建议 Adapter 与 Grounded Synthesis
> 交付方式：保留 19 个原子任务，但按 Kernel → Capture → Lite 纵向闭环 → Capability Modules 重编；本计划取代旧的固定重流水线顺序，不追加 Task 20。
> 2026-08-19 评审修订：补齐 Capture 前模型 Binding 权威来源（T2/T3/T4/T5/T7/T8）、五种领域 Record 与 `ModelPortFailure` 归属、Runner 安全 conformance、版本化关系规则注册表与 citation 负向 fixture；T8 拆为 A/B 两个验收里程碑，仍保持 19 个逻辑 Task。

## 1. 目标与边界

本计划把以下五份正式设计作为同一个 Protocol 1.1.0 交付：

- `2026-08-18-harness-slim-profiles-design.md`；
- `2026-08-18-intent-to-prd-capture-design.md`；
- `2026-08-18-designset-lifecycle-design.md`；
- `2026-08-18-provable-tdd-protocol-design.md`；
- `2026-08-19-model-advisory-adapters-design.md`。

实施完成后：

1. `new/adopt` 先由用户选择并确认 Lite、Standard、Governed；`iterate` 使用当前项目 Profile revision。
2. 所有 Profile 共用 Evidence Kernel 和 managed Capture，但只运行 CapabilityPlan 中真实启用的 Module。
3. Lite 先形成可用的最小纵向闭环，不产生未启用 Module 的空壳工件。
4. Standard/Governed 在同一 Kernel 上增加 Impact、Design、Evaluation、Strict TDD 和 Audit，而不是复制 Orchestrator。
5. Plan 从 accepted PRD、冻结 ImpactSet、accepted DesignSet 和 final CapabilityPlan 编译；Criterion、Test seed、Assertion、Task、Evidence、Verdict 全链唯一可追踪。
6. Agent 自述、transcript、Live telemetry 和文件时间戳都不能替代 Ledger Evidence。
7. Impact、Design Review、Plan 和 Feedback 的模型输出始终是候选；四类跨阶段摘要统一由固定 purpose 的 `GroundedSynthesisPort` 生成并逐 claim 引用来源。
8. Standard/Governed 对当前 Operation 适用的模型槽位强制配置 Provider；Lite 未启用槽位零 Invocation、零 Result、零空壳 Evidence。
9. Capture 前的模型槽位（`project_discovery` 与 Capture 阶段 `approval_brief`）由 ProfileDecision 级 Capture-scope binding 持有；accepted PRD 后的槽位由 CapabilityPlan 持有；两类 binding 使用同一 Schema，但作用域互不重叠。

本计划不包含多人并行设计、分布式租约、多人投票审批、Markdown 权威源、未启用 Capability 的占位工件，也不改写已完成 Protocol 1.0 的历史事实。

## 2. 实施纪律

### 2.1 测试先行

每个 Task 必须遵守：

```text
新增或修改测试并证明失败
  → 最小实现
  → 目标测试通过
  → 相关包测试通过
  → pnpm verify
  → 提交
```

在 Harness 自身 Provable TDD 尚未可用前，提交说明或任务 Evidence 必须记录 Red/Green 命令和结果。Task 16 完成后，后续适用任务必须通过 Harness dogfood 生成可重放 Baseline/Red/Green 证据，不能只引用开发纪律。

### 2.2 权威边界

- Ledger/typed runtime records 保存权威状态；Graph 只保存 accepted 工程事实；Markdown/Dashboard 是 Projection。
- Workflow Engine 只理解 CapabilityPlan DAG、checkpoint、typed result 和 invalidation，不判断 Profile 名称。
- Profile/Capability Compiler、Capture Coordinator、Design Coordinator、TddController 分别保持一个窄 Interface；CLI/Dashboard 不复制状态机。
- 模型 Adapter 只拥有生成、评审或提炼；领域 Coordinator/Compiler 拥有校验、风险上界、路由、失效和提交，人类或版本化 Policy identity 拥有真实 ApprovalDecision。
- 每个审批必须绑定真实业务对象及 digest，不按 phase 固定批准次数。
- 所有新集合进入 digest 前规范排序；时间和 Live telemetry 不进入语义 digest。

### 2.3 通用验证

每个 Task 至少运行目标测试和相关包 typecheck。进入主干前统一运行：

```bash
pnpm format:check
pnpm lint
pnpm build
pnpm typecheck
pnpm test
pnpm verify
```

涉及安全、恢复、Dashboard 或打包的 Task 还要运行相应专项命令：

```bash
pnpm test:security
pnpm test:fault
pnpm test:e2e
pnpm test:e2e:dashboard
pnpm pack:smoke
```

## 4. Task 1：Protocol 1.1 Registry、Canonical 基础与 Schema Plumbing

**目标**：只建立五份设计共享的 Protocol registry、canonical primitives、record envelope 和 JSON Schema 注册/导出基础，不在一个串行任务中实现全部领域 Schema。

**主要落点**：`packages/core/src/schema/`、`packages/core/src/identity/`、`packages/core/schemas/` 和 Protocol registry。

**测试先行**：

- Protocol 版本、record envelope、Schema registry 和导出边界；
- 集合乱序仍产生同一 digest，语义变化必然改变 digest；
- domain tag、版本和 canonical input 不同必然产生不同 identity；
- 未注册 Schema、未知 Protocol 和导出漂移 fail closed。

**实现**：定义 Protocol 1.1 registry、公共 record envelope、canonical JSON/digest/id helpers、Schema 注册与生成工具。Profile/Capability/ModelProviderBinding Schema 归 T2/T3，Capture 归 T4/T6/T7，DesignSet/Design Review 归 T11/T12，Assertion/Plan Proposal/TDD/Evidence 归 T13/T16，模型调用记录归 T8，Protocol 1.0 reader 归 T17，状态投影 contract/领域映射分别归 T3/T16。

**完成条件**：共享基础可由领域 Task 独立扩展和测试；T1 不拥有任何领域状态机或兼容迁移语义，不再是五份设计全部 Schema 的串行瓶颈。

## 5. Task 2：Project Profile 记录、选择与风险 Override

**依赖**：T1。

**目标**：实现三档 ProjectProfile 的 append-only 权威记录和 new/adopt/iterate 选择语义，但暂不运行高级 Module。

**测试先行**：

- new/adopt 缺少交互选择或 `--profile` 时返回 `input_required`；
- iterate 使用当前 revision，项目降级只影响未来 Operation；
- Recommendation 可 Override，但 Policy required/deny 不可覆盖；
- Override 绑定 iteration/risk/digest，scope drift 后失效；
- 同一 decision idempotency key 不产生重复记录。
- Profile/Recommendation/Decision records 的严格 Schema、canonical ordering 和 golden fixtures。
- Lite、Standard、Governed 的模型槽位默认、required/optional 和 `block | projection_finding` 失败模式符合 Profile 矩阵；`iteration_narrative` 不得反向阻塞 Snapshot。
- Capture-scope binding 在 Capture 启动前提交，绑定 ProfileDecision、Policy、配置、baseline 和版本摘要；同一 slot/purpose 不得同时存在于 Capture-scope 与 CapabilityPlan binding。

**实现**：`ProjectProfileRecord`、`ProfileRecommendationRecord`、`ProfileDecisionRecord` 及其 JSON Schema，三档 registry、风险推荐、模型槽位 Profile defaults、Capture-scope `ModelProviderBinding` 记录（覆盖 `project_discovery` 与 Capture 阶段 `approval_brief`）和旧项目显式迁移。

**完成条件**：项目档位选择是显式、可恢复、可审计事实，不存在静默 Standard 默认。

## 6. Task 3：Capability Registry、依赖闭包、Compiler 与 Operation DAG

**依赖**：T1、T2。

**目标**：从 Profile、风险、Policy、Provider 和 accepted bindings 确定性编译 CapabilityPlan。

**测试先行**：

- dependency closure property tests；
- 激活 `strict_tdd` 自动补齐 `impact_analysis → design_governance`、structured Gate 和 isolated workspace；
- DAG 循环、缺 Provider、冲突 output、非法 deferred 全部阻塞；
- Standard `strict_tdd` provisional → final 只允许在 accepted DesignSet 后发生；
- 通用 DAG 固定表示 `verify → [evaluate?] → snapshot`；
- 未启用 Module 零 contributor invocation、零工件、零 Approval。
- `CapabilityStatusProjection` 只允许 Slim 通用五态，未知通用状态 fail closed；领域状态映射由 owning Module 注册。
- Standard/Governed 当前 Operation 在 accepted PRD 之后适用的领域 Port 与 Grounded purpose 都编译显式 `ModelProviderBinding`；缺 Provider、未知 purpose、版本/预算冲突或非法 failure mode 阻塞。Capture 前槽位不进入 CapabilityPlan，由 T2 的 Capture-scope binding 持有；编译器确定性验证两类 binding 作用域不重叠。
- Lite 未启用模型槽位时不生成 binding；启用后同样执行 provider closure，不得用 Manual、确定性假结果或另一模型静默降级。

**实现**：Capability registry、依赖/provider closure、`ModelProviderBinding`/slot registry、approval objects、invalidation graph、provisional/final `CapabilityPlanRecord`、相关 Schema、DAG contributor Interface 和通用 `CapabilityStatusProjection` contract。Binding 固定 port/purpose、provider/config、prompt/Schema、budget 和 failure mode digest。

**完成条件**：同一 canonical 输入产生同一 plan digest；进入 Plan 前 CapabilityPlan 必须 final。

## 7. Task 4：Managed Capture Coordinator 与可恢复状态机

**依赖**：T1。

**目标**：以 `PrdCaptureCoordinator.advance()` 作为 CLI、Dashboard、Orchestrator 共用的唯一推进 Interface。

**测试先行**：

- 15 个 `CaptureState` 的合法/非法迁移矩阵；
- `review_provider_required` 只能表示为 `state: blocked` 与 typed `blocked_reason`，不得被接受为状态；
- `blocked_reason` 当且仅当 blocked 必填；
- crash、resume、expected digest conflict、Decision 已提交未消费；
- 任何 Capture 阶段模型调用发生前，Operation、Session 与全部 Capture-scope binding digest 已持久化。
- Session revision append-only，重复命令幂等。
- Capture Session、Question、Answer、Invocation、Checkpoint 和 typed blocker records 的严格 Schema/canonical fixtures。

**实现**：Capture Session、Question、Answer、Invocation、Checkpoint records 及其 JSON Schema，typed `CaptureBlockReason`、恢复命令和 ApprovalDecision consumption。

**完成条件**：任何 Port 调用前 Session/Operation 已提交；刷新或重启后能只从 Ledger 恢复。

## 8. Task 5：受控 Project Context 与 Proposal/Review 隔离

**依赖**：T4。

**目标**：自动读取受控项目上下文，为 Proposal 与 Review 编译相互独立的 ContextBundle，并建立 `GroundedSynthesisPort` 的固定四 purpose/四 Schema 契约。

**测试先行**：

- manifest/README/Gate/Graph/ADR/API/Schema/Policy 的 Profile 选择矩阵；
- path traversal、symlink、secret、binary、oversize、prompt injection fixtures；
- Proposal/Review 可以源文件重叠，但 bundle id/digest/conversation 不得复用；
- baseline 漂移使 Bundle 及下游失效；
- Adapter 无项目文件或 Ledger 直接读取权限。
- `project_discovery` 只能返回带来源的项目事实、候选 Capability/Gate 和 confidence，不得直接写 Graph/Profile/CapabilityPlan；所有业务 claim 引用当前 Bundle。
- `project_discovery` 只消费 T2 提交的 Capture-scope binding；binding 缺失或漂移按 typed failure 阻塞，不从 CapabilityPlan 或临时配置推断。
- 动态 purpose、动态输出 Schema、跨 purpose 会话/history/cache 复用和 source digest 不匹配全部被拒绝。

**实现**：`ProjectContextPort`、local-git/in-memory adapters、purpose、budget、selection、redaction、provenance 和失效记录；定义 `GroundedSynthesisPort`、四个固定 purpose 及其版本化联合输入/输出 Schema 与 `GroundedSynthesisRecord`。T5 用 InMemory fake 完成 `project_discovery` input compiler、Validator 和 Capture/Capability 推荐消费契约；外部 Provider 的受管调用、Evidence 和恢复在 T8 接线，避免让 T5 反向依赖尚未存在的 Runner。

**完成条件**：上下文最小、可解释、可复验，Proposal 与 Review 不形成同会话自评。

## 9. Task 6：PrdProposalPort、确定性硬门禁与 Manual Capture UX

**依赖**：T5。

**目标**：让结构化 `PrdProposal` 成为 PRD 唯一权威源，并使 Lite Manual 录入真正轻量。

**测试先行**：

- Manual、in-memory、模型和 `LegacyIntentInterpreterAdapter` conformance；
- Coordinator-issued entity id、lineage、SourceBinding 和 stable revision；
- Schema/reference/conflict/open-question/test-first-readiness hard gates；
- 非原子 Criterion 必须澄清，不能留给 Planner 做 1:N Assertion 拆分；
- Manual 表单优先显示上下文预填、差异和缺失项；
- telemetry 不进入 Proposal semantic digest；
- Coordinator 重算 criterion semantic digest；Adapter 携带的 digest 不匹配时确定性拒绝；
- `InterpretedIntent`、`ClarificationOffer` 和 `undefined` 按兼容规则确定性映射；
- 新 `capture.proposal` 与旧 `interpret` 同时配置时返回 configuration error，不设隐式优先级；
- Legacy 输出仍经过 Proposal Schema、硬门禁、独立 Review 和批准，不能直接生成 RequirementBaseline。

**实现**：`PrdProposalPort`、ManualPrdProposalAdapter、LegacyIntentInterpreterAdapter、Proposal/criterion semantic digest Schema、deterministic validators、typed questions/findings、兼容配置校验和 Capture UX telemetry。

**完成条件**：无模型时 Manual 是完整默认路径；Generic Interpreter 不再自动包装低质量 Requirement；旧 IntentInterpreter 在一个 major 兼容期内可用但不能绕过新质量链。

## 10. Task 7：独立 Review、Risk、批准与 Accepted PRD 原子提交

**依赖**：T6。

**目标**：完成 Capture 质量闭环并物化稳定 Criterion/Test seeds。

**测试先行**：

- hard gate 失败不调用 reviewer；
- Proposal/Review invocation/context/prompt/conversation/Evidence 独立；
- Review revise/clarify/blocked、Manual Review input 和 Provider 缺失恢复；
- low/non-material/high-confidence Policy auto approval 与 material human approval；
- object digest 漂移使 Approval 失效；
- accepted PRD、RequirementBaseline、Graph、bindings、checkpoint 原子提交；
- Criterion continues 稳定复用 id/Test seed，Question→Answer→Criterion lineage 可复验。
- 存在人工批准时，`approval_brief` 绑定已提交审批对象并逐 claim 引用；摘要不能修改对象 digest、风险、范围或建议自动通过。
- Standard/Governed 的 required `approval_brief` Provider 缺失或耗尽受控重试后进入 typed blocked；PrdReviewPort 是否使用模型仍遵循 Capture 自身的 Adapter/Profile 规则，Lite Grounded 槽位仅在已启用时调用。

**实现**：`PrdReviewPort`、RiskAssessment/Profile Recommendation、immutable `AcceptedPrdRecord`、从 criterion id 确定性派生 Test id，以及 Capture Approval 的 `approval_brief` input compiler（只消费 T2 Capture-scope binding，不从 CapabilityPlan 推断）、Citation Validator 和 Read projection。T7 以 InMemory fake 验证消费契约；外部 Provider 调用由 T8 的 Runner 接线。摘要 invocation/result 不进入被审批对象的语义 digest。

**完成条件**：accepted PRD 不可修改；失败事务不留下部分 baseline 或 graph facts。

## 11. Task 8：Workflow Engine DAG 化、受管模型调用与 Orchestrator 深模块拆分

**依赖**：T3、T7。

**目标**：移除固定 phase 主流程，让 Workflow Engine 执行 CapabilityPlan 中实际存在的节点，并提供所有领域模型 Port 共用、但不向领域暴露的受管调用深模块。本 Task 规模超出单原子提交，拆为两个验收里程碑与两个提交，仍为一个逻辑 Task：

- **T8-A**：Workflow Engine DAG 化、checkpoint/resume、Orchestrator 深模块拆分与兼容 facade；
- **T8-B**：`ManagedModelInvocationRunner`、调用记录、安全隔离、失败契约与 T5/T7 接线。

**测试先行（T8-A）**：

- Lite、Standard、Governed 三种 DAG fixture；
- optional node 缺席时无调用、无 checkpoint、无空壳事件；
- node crash/resume、awaiting approval、authoritative commit；
- capability upgrade 失效最早必要节点并确定性恢复；
- Engine 测试不需要构造 Profile-specific 分支。

**测试先行（T8-B）**：

- `ModelInvocationPlanned → Started → Completed/Failed/Indeterminate → Validated/Rejected → Consumed/Invalidated` 的恢复、重试、对账和漂移矩阵；调用前必须先持久化 Operation/checkpoint 与全部 binding digests（含 Capture-scope binding）。
- 每次 Port/purpose 调用独立 prompt、Schema、budget、conversation、run identity 和 Evidence；可以共用 vendor/model/executable，但禁止隐藏历史或跨 purpose cache。
- timeout、budget、无效输出、缺 citation、binding drift、independence violation、version mismatch、uncertain、policy denied、`provider_required` 和 `provider_unavailable` 统一映射 typed failure；`ModelPortFailure` 全枚举具有严格 Schema 与 canonical fixtures。
- Runner 安全 conformance：Provider cwd 必须是隔离临时目录；项目 workspace、Ledger、Evidence sink 和宿主 cwd 对 Provider 不可见；环境变量使用 allowlist；endpoint、redirect、network origin 和 credential 使用 Policy allowlist；输出递归拒绝 command/tool/unknown field，并限制尺寸、嵌套深度、数组与字符串长度；原始敏感输出不得进入 Dashboard；artifact retention 与清理策略可复验。
- 统一 citation 负向 fixture：引用真实存在且 digest 正确、但模型给出语义错误结论时，citation_integrity 校验通过，且不得改变风险、批准、Impact、Design、Plan、Verdict 等任何权威状态；该 fixture 由 T8-B 提供，T10/T12/T17/T19 分别消费验证领域边界。

**实现（T8-A）**：DAG node contract/runner/checkpoint/typed result，从现有大型 orchestrator 抽出 Kernel Coordinator、Capability Compiler 和 Module contributors，保留兼容 facade。

**实现（T8-B）**：内部 `ManagedModelInvocationRunner`、`ModelInvocationRecord`、`ModelPortFailure` 严格 Schema、预算/隔离/输出上限/重试/对账/Evidence 与恢复模块，并把 T5/T7 已定义的 `project_discovery`/`approval_brief` 契约接入受管调用。Runner 不是公共 generic model port，领域继续使用各自严格 Interface/Schema。

**完成条件**：Engine Interface 足以测试所有 DAG；删除任一未启用 Module 不影响 Kernel happy path；Runner 安全 conformance 全部为机械化断言。

## 12. Task 9：Lite Kernel-only 首个完整纵向闭环

**依赖**：T8。

**目标**：在高级 Module 之前交付 Capture → Plan → Context → Execute → Verify → Snapshot。

**测试先行**：

- new/adopt/iterate/resume Lite happy path；
- required project Gates 产生 Evidence，Agent 自述不能通过验收；
- ImpactSet、DesignSet、Evaluation、TDD Contract/Cycle 的 Port、record、event、approval 均为零；
- 五个新模型 Port、四种 Grounded purpose、Provider binding、Invocation、Result 和模型 Evidence 均为零；
- CLI/Dashboard happy path 不要求理解 Node、Edge、digest、Cycle；
- 单 Requirement Capture 指标可记录和导出。

**实现**：Kernel-only deterministic Planner、Context、Agent Grant、Gate/Evidence、Snapshot/Finding、`inactive_by_profile` Read API 和一次驱动入口。Lite 只有在用户/Policy 显式激活对应 capability 后才编译模型 binding，否则完全不经过受管模型调用。

**完成条件**：Lite 不是隐藏后的完整重流水线；自动测试机械证明零 optional artifacts。

## 13. Task 10：Impact Advisory、Independent Evaluation 与 Advanced Audit Module Contributors

**依赖**：T8。

**目标**：把既有 Impact/Evaluation/Audit 接入 Capability Module contract，并在确定性传播之后增加只可增补的 `ImpactAdvisoryPort`。

**测试先行**：

- Impact contributor 的 input/output/checkpoint/invalidation；
- Evaluation 未启用时 `verify → snapshot`，启用时 `verify → evaluate → snapshot`；
- Evaluation/Audit 未启用时零 runner/event/evidence；
- Standard/Governed 默认解析出的 DAG 包含对应节点；
- Finding 风险信号可以请求升级，但不能自行批准。
- Impact 固定执行 `propagate → advise → validate → approve`；模型不能删除确定性 entry、降低默认/路径风险、改写传播方向或激活规则禁止的 inferred edge。
- 每个候选 Impact/edge/risk/missing fact 必须引用当前 Graph/PRD/Source；`SemanticSeedProvider` 仅作为候选检索来源，不形成第二权威图。
- Provider 缺失/失败、降风险尝试、无来源 candidate、过期关系规则和 input drift 按 typed failure/finding 恢复；模型不得跳过完整 ImpactSet 校验与批准。
- 输入绑定 `relation_rule_registry_version + digest`，不允许硬编码关系数量；注册表版本漂移按 typed failure 恢复。
- 消费 T8 统一 citation 负向 fixture：引用合法但结论错误的 Advisory 不改变权威 ImpactSet、风险或批准状态。

**实现**：三个 ModuleDefinition/contributor、既有引擎适配和 Read API 通用/领域状态投影；新增 `ImpactAdvisoryPort`、purpose-bound input compiler、严格结果 Schema、additive merge validator、InMemory/model/dsh adapters 与 `ImpactAdvisoryRecord`。通过校验的增补与确定性传播结果合并后，仍只批准完整 ImpactSet。

**完成条件**：三项能力可以独立启停，Engine 和 Kernel 无 Profile 条件分支。

## 14. Task 11：DesignSet Schema、主责覆盖与纯 Validator

**依赖**：T10。

**目标**：实现 DesignSet、设计资产、关系边、无歧义 Test Strategy coverage，以及独立 Design Review 所需的 Finding/coverage/result Schema。

**测试先行**：

## 17. Task 14：Grounded Context 与 ExecutionPreflight 的 Capability 条件绑定
