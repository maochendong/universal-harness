# SpecKit Comparative Design and Task Cards

**Status**: proposed
**Date**: 2026-08-14
**Scope**: M1.x enhancements; no protocol changes required for directions 1-3, a minor schema-facing change only for direction 4

This document compares SpecKit's specification-driven workflow (as used in
the Spec-Driven-Design project) with Universal Harness, and derives four
engineering directions from it. Each direction is specified as a comparative
design (what SpecKit form is borrowed, how the harness realizes it in its own
idiom, which harness differences are kept on purpose) plus an independently
committable task card.

## 1. Reference Material

SpecKit side (Spec-Driven-Design project):

- `.claude/commands/speckit.md` -- the workflow definition: four phases
  (Constitute, Specify, Plan, Implement), a quality gate per phase
  (deterministic score, threshold 85), a human checkpoint per phase, T001-style
  numbered tasks, and progress tracking (`T005 <- Current`, `[####----] 80%`).
- `.speckit/TASKS.md` -- the human-facing task list: numbered tasks grouped by
  sprint, checkbox-style completion, acceptance gates (Q-1..Q-9) tracked next
  to the tasks they constrain.
- `.speckit/PLAN.md` -- the technical plan: architecture, task breakdown with
  estimates, dependency notes, and a strategy section (backend-first waves).
- `.speckit/state.json` -- machine-readable workflow state: current phase,
  per-sprint status, acceptance gate status, `lastVerified` provenance.
- `.speckit/validate-spec.js` / `validate-plan.js` -- deterministic gate
  scripts: structural regex checks over the documents, scored against
  thresholds, blocking exit codes, JSON reports under `.speckit/quality/`.
- `outputs/agent-centric/03-detailed-plan.md` -- a dependency-graph and
  Wave-partitioned plan instance (F-001 --> F-002 chains, independent tasks
  marked as parallelizable).

Harness side (current state):

- Graph `Task` nodes and `DEPENDS_ON` edges (`packages/core/src/schema/node.ts`,
  `packages/graph/src/integrity.ts` relation matrix) already model numbered,
  dependent work items; `ExecutionPlan` content already carries a `tasks[]`
  array that `validatePlanProposal` accepts with dependencies
  (`packages/runtime/src/planning/execution-plan.ts`).
- The orchestrator currently compiles exactly one task per iteration
  (`taskSpecificationFor` in `packages/runtime/src/orchestration/orchestrator.ts`).
- Approval gates exist at capture (requirement baseline) and impact (impact
  set freeze) -- human checkpoints are already protocol, not convention.
- The audit family (`packages/runtime/src/audit/auditor.ts`) already plays the
  role of SpecKit's `validate-*.js` scripts: deterministic checks over
  authoritative state, feeding the Finding -> human review cascade
  (`commitAuditFindings` in the orchestrator).
- Managed projections (`packages/runtime/src/projection/managed-output.ts`)
  already render human-facing Markdown under `.harness/views/` with drift
  detection and overwrite approval; the graph remains the only source of
  truth and the rendered file is disposable.

## 2. Direction 1: tasks.md Projection

**SpecKit form borrowed.** `.speckit/TASKS.md`: one numbered, checkboxed task
list a human can scan in seconds, with completion state and dependencies
inline (`T002: Database schema (4h) [depends on T001]`), plus the `[P]`
parallel marker used in spec-kit style task lists for independent tasks.

**Harness realization.** A deterministic projection, `renderTasksProjection`,
next to the existing PRD/plan renderers (`adapters/projection-markdown/`),
written through the managed-output channel to `.harness/views/tasks.md`.
Numbering is derived, not stored: tasks of an `ExecutionPlan` are sorted
topologically over `DEPENDS_ON` edges (ties by id) and numbered `T001...`;
a task gets `[P]` when no dependency path connects it to any sibling.
Checkboxes reflect authoritative state: a task is `[x]` when a terminal,
accepted Run `EXECUTES` it with a success outcome, derived from the graph --
never from the file itself. The projection is regenerated by the completing
snapshot phase (same hook that already refreshes audit findings), so it can
never go stale silently; `detectProjectionDrift` catches manual edits and the
managed write refuses to overwrite them without an explicit approval.

**Differences kept.**

- Graph is the only source of truth: `tasks.md` is a view, byte-regenerable
  at any time. SpecKit treats `TASKS.md` as editable state; the harness never
  reads it back. A hand edit is drift, not input.
- Completion is provenance-bound (Run/evidence records), not a checkbox a
  human ticks. `[x]` means "the ledger proves it", not "someone said so".

## 3. Direction 2: Multi-Task ExecutionPlan

**SpecKit form borrowed.** The Plan phase in `speckit.md` and the
`03-detailed-plan.md` instance: decomposition into small tasks (SpecKit
targets 2-8h; here: 1-3 files, independently verifiable), an explicit
dependency graph, and Wave partitioning so independent tasks are visible at a
glance. Also the progress display from `speckit.md`
(`Implement (11/15 tasks)`), which maps naturally onto `harness status`.

**Harness realization.** `phasePlan` stops hard-coding a single task:
`taskSpecificationFor` becomes a deterministic decomposition of the approved
impact set and requirement baseline into N task specifications (1-3 files
each, each with its own acceptance slice and required gates, `DEPENDS_ON`
edges for ordering). `validatePlanProposal` and the plan records already
accept this shape -- the change is in proposal construction and in the phase
loop, not in the schema. The whole plan is still frozen behind one approval
(the impact set approval already covers it; no new gate). The execute phase
iterates tasks in topological order: one Task Envelope, run, gate suite and
evaluation per task, each committed idempotently so resume continues at the
first unfinished task. `deriveProjectStatus` gains a task-progress facet
(`tasks_completed` / `tasks_total` for the open iteration) rendered as
`2/3` in `next_action` while an iteration is in flight.

**Differences kept.**

- Approval gate, not free flow: SpecKit waits for a plan review out of
  convention; the harness binds the exact approved plan digest and refuses to
  execute a drifted one.
- Decomposition output is still graph data: tasks are nodes with
  `CONTAINS`/`DEPENDS_ON` edges and digests, so the audit family and the
  impact analysis can reason about them. SpecKit's dependency graph lives
  only in prose.

## 4. Direction 3: analyze-Style Coverage Audit

**SpecKit form borrowed.** The `validate-spec.js` / `validate-plan.js`
deterministic gates: structural cross-checks between the specification and
the plan (does every requirement land in a task? does the plan cover the
contract surface?) with machine-readable verdicts, and the acceptance-gate
tracking in `state.json` (Q-1..Q-9) that keeps cross-document coverage
visible until a human closes it.

**Harness realization.** Three new deterministic rules in
`packages/runtime/src/audit/auditor.ts`, in the existing style, feeding the
same Finding -> human review cascade (warnings or blockers per the rule, via
`commitAuditFindings`):

- `api_contract_coverage` (warning): entries of the accepted API contract
  document (deterministic heading/endpoint extraction) with no Task whose
  expected outputs reference them. Extends `missing_design_artifact` -- that
  rule checks the document exists; this one checks its content is planned
  against. The existence check is **not** duplicated: when no contract
  document exists, this rule stays silent and lets
  `missing_design_artifact` speak.
- `task_orphan` (blocking): a proposed/accepted Task with no `IMPLEMENTS`
  edge to any Requirement. This is the inverse direction of the existing
  `traceability_gap` (accepted Requirement with no Task `IMPLEMENTS` it) and
  becomes meaningful once direction 2 lands multi-task plans with per-task
  `IMPLEMENTS` edges. The rule reuses the edge-traversal pattern of
  `auditTraceability`; it never re-flags a Requirement-side gap.
- `task_stale` (blocking): a Task whose terminal Run exists but has no
  passed, current evidence verdict bound to it. Overlap control with
  `missing_verification`: that rule targets accepted **Test** nodes without
  evidence; `task_stale` targets **Task** nodes and follows the
  Run -> Evidence (`PRODUCES`) / EvaluationCase (`EVALUATES`) chain instead
  of the Test `SUPPORTS` chain. The two rules share the
  evidence-freshness vocabulary (`findingClosableBy`, current-digest
  semantics) but fire on disjoint node sets.

**Differences kept.**

- Verdicts enter the Finding cascade and wait for human review; nothing is
  auto-fixed. SpecKit's gates block a write hook; harness findings block (or
  warn on) the iteration through the status derivation, with the ledger as
  their proof.
- Scores are not borrowed: SpecKit's 85-point quality score is heuristic
  prose metering. The harness keeps binary, explainable checks whose
  subjects are exact node ids.

## 5. Direction 4: clarify Up Front (low priority)

**SpecKit form borrowed.** The Specify phase's interactive elicitation and
its "Open questions" section: ambiguity is surfaced *before* planning, as
structured questions with explicit options, never silently resolved.

**Harness realization.** The capture phase already has the escape valve:
`captureRequirements` can return `clarification_required`, and the CLI
surfaces `input_required` with `ClarificationQuestion`s. The gap is that
questions are free text. Direction 4 gives `ClarificationQuestion` an
optional `options: string[]` (2-4 choices plus "other"), lets the intent
interpreter port emit them, and renders them in the `--json` outcome so a
driver can answer mechanically. Deterministic fallback: when no interpreter
is present, ambiguity still produces the plain question form, never an
implicit answer.

**Differences kept.**

- Answering is a human act either way: a clarification answer re-enters
  through a new intent capture with its own baseline approval; the harness
  never threads an answer around the approval gate.

## 6. Cross-Cutting Differences the Harness Keeps

- **Graph/ledger provenance**: every borrowed artifact (task list, progress,
  coverage verdict) is derived from committed graph state and regenerable;
  files under `.harness/views/` are projections, and the audit trail for any
  number shown to a human is one digest lookup away.
- **Approval gates**: SpecKit's checkpoints are conversational; the harness
  binds approvals to exact object digests and invalidates them on drift.
- **Evidence chain**: completion and coverage claims are backed by
  Evidence records bound to code/artifact digests; stale evidence reopens
  the question instead of lingering as a green checkmark.

## 7. Task Cards

Ordered for implementation: 1 (projection), 3 (multi-task plan), 2 (analyze
rules), 4 (clarify). Card ids below follow that order.

### T1 -- tasks.md projection from graph Task nodes

- **Goal**: render `.harness/views/tasks.md` (SpecKit-style numbered,
  checkboxed, dependency-annotated task list) from the authoritative graph
  and regenerate it at every completing snapshot.
- **Modules/files**: new `renderTasksProjection` in
  `adapters/projection-markdown/src/` (next to `renderPlanProjection`);
  managed write + drift via `packages/runtime/src/projection/managed-output.ts`
  and `packages/runtime/src/projection/drift.ts`; hook in `phaseSnapshot` in
  `packages/runtime/src/orchestration/orchestrator.ts`; golden fixture under
  `tests/golden/projections/`.
- **Acceptance assertions**:
  - For the fixture graph of a completed iteration, the rendered output
    equals the committed golden file byte for byte.
  - Two consecutive snapshot-phase regenerations produce byte-identical
    files (idempotent).
  - A manual edit of `.harness/views/tasks.md` makes
    `detectProjectionDrift` report `stale`/`modified` and the managed write
    refuses overwrite without approval.
  - A task with a terminal accepted Run renders `[x]`; a task with a
    `DEPENDS_ON`-free sibling set renders `[P]`; dependency annotation shows
    `depends on T001` ids.
- **Dependencies**: none. Full dependency/`[P]` rendering becomes observable
  with T2, but the renderer already reads `DEPENDS_ON` edges correctly today.
- **Size**: M.

### T2 -- multi-task ExecutionPlan with per-task progress

- **Goal**: `phasePlan` decomposes the approved impact set into N small task
  specifications (1-3 files, independently verifiable, `DEPENDS_ON`
  annotated); one approval covers the whole plan; execute/verify/evaluate
  advance task by task; status shows `done/total` progress.
- **Modules/files**: `taskSpecificationFor`, `phasePlan`, `phaseExecute`,
  `phaseEvaluate` in `packages/runtime/src/orchestration/orchestrator.ts`;
  decomposition rules in `packages/runtime/src/planning/execution-plan.ts`
  (proposal side; `validatePlanProposal` already accepts N tasks and
  dependencies); progress facet in
  `packages/runtime/src/status/status.ts`; resume semantics in
  `packages/runtime/src/workflow/resume.ts` (first-unfinished-task rule).
- **Acceptance assertions**:
  - A fixture iteration whose plan has 3 tasks and 2 `DEPENDS_ON` edges
    passes graph integrity (`CONTAINS` + `DEPENDS_ON` compatibility) and
    commits exactly one approval request for the whole plan.
  - Executor envelopes are issued in topological order (recorded call order
    in the orchestrator test).
  - After two of three tasks complete, `deriveProjectStatus` reports
    progress `2/3` and `next_action` references the third task.
  - A resume after a simulated crash re-executes only the unfinished tasks
    (no duplicate Run nodes).
- **Dependencies**: none hard; T1 renders richer output once this lands.
- **Size**: L.

### T3 -- analyze-style coverage audit rules

- **Goal**: add `api_contract_coverage`, `task_orphan` and `task_stale` to
  the auditor, deduplicated against `missing_design_artifact`,
  `traceability_gap` and `missing_verification`, feeding the existing
  Finding -> human review cascade.
- **Modules/files**: `packages/runtime/src/audit/auditor.ts` (rules +
  `AUDIT_FINDING_KINDS`); contract-entry extraction helper (deterministic,
  heading/endpoint based) in the same file or
  `packages/runtime/src/audit/`; tests in
  `packages/runtime/test/audit/auditor.test.ts`.
- **Acceptance assertions**:
  - A fixture graph with a Task lacking any `IMPLEMENTS` edge yields exactly
    one `task_orphan` finding with that task id as subject; a graph whose
    only gap is Requirement-side yields `traceability_gap` and **not**
    `task_orphan`.
  - A fixture graph with a contract document listing 3 endpoints, 2 covered
    by tasks, yields one `api_contract_coverage` finding naming the
    uncovered entry; with no contract document present, the rule is silent
    (only `missing_design_artifact` fires).
  - A fixture graph with a terminal Run but no passed current evidence
    yields `task_stale`; the same graph does not produce
    `missing_verification` duplicates for Task subjects (disjoint node
    sets), and vice versa for Test subjects.
  - Findings are committed by `commitAuditFindings` with the correct
    blocking flag (`task_orphan`/`task_stale` blocking, contract coverage
    warning) and dedupe across two iterations.
- **Dependencies**: T2 (per-task `IMPLEMENTS` edges and multi-task runs give
  `task_orphan`/`task_stale` their subjects); the rules must be written to
  stay silent on single-task legacy graphs where appropriate.
- **Size**: M.

### T4 -- clarification questions with options

- **Goal**: capture-phase ambiguity surfaces as structured clarification
  requests carrying 2-4 explicit options, before any planning starts.
- **Modules/files**: `ClarificationQuestion` in
  `packages/runtime/src/requirements/capture.ts` (optional `options` field);
  `IntentInterpreter` type and `input_required` rendering in
  `packages/runtime/src/orchestration/orchestrator.ts`; CLI surface in
  `packages/cli/src/commands/iterate.ts` / runtime-service mapping; schema
  touch only if the question shape is persisted (check
  `packages/core/schemas/` first).
- **Acceptance assertions**:
  - An ambiguous fixture intent yields `input_required` whose questions each
    carry 2-4 options plus an "other" escape; identical intent yields
    byte-identical questions (deterministic).
  - A fixture with the generic interpreter still produces the plain
    optionless question form (no regression for free-text capture).
- **Dependencies**: none; independent of T1-T3. Lowest priority.
- **Size**: S.
