Reference · Evidence first

从一句声称到可放行结论

验证不是“找到一个绿色测试”。它是把声称拆成作用域，再用当前源码、调用链、测试、Ledger 和发布证据逐层收敛。

六步验证法

1
改写声称

把“功能完成”改写为可判定句：哪项能力、哪个 Profile、哪条生产路径、哪个 commit、哪个环境。

2
找到权威定义

读取 Schema、Registry、Compiler 或 Validator；文档用于定位，不替代代码裁决。

3
追生产消费者

从 CLI/Dashboard 入口追到 Coordinator、Runner 和守卫；孤立单测不能证明生产接线。

4
复跑最小测试

先用紧贴不变量的 targeted test 缩短反馈，再按风险决定是否运行 E2E、fault 或 release。

5
核对权威证据

检查 Ledger、Snapshot、Evidence digest、source commit、平台和 Provider；不要把日志或 projection 冒充事实。

6
写范围化结论

明确 passed、partial、not_verified 与 blocker，并指出证据不能证明什么。

证据梯子

证据 能证明什么 不能单独证明什么
设计文档 / README 目标、术语、声称和预期边界 当前实现、生产接线或运行通过
类型 / Schema / Registry 契约存在、词表封闭、不变量可表达 真实入口已经消费
单元 / 属性测试 组件行为和 fail-closed 边界 打包 CLI、外部 Provider 或发布环境
生产接线测试 / E2E 入口、Coordinator、Runner 与守卫形成闭环 未覆盖的平台或真实外部依赖
Ledger / Snapshot / Evidence 指定 Operation 在指定 commit 上留下权威完成链 其他 commit、Profile 或平台
同 commit 发布矩阵 目标平台工件与发布门禁通过 未来版本或未纳入矩阵的环境

推荐结论模板

VERDICT 
结论：{passed | partial | not_verified | blocked}
对象：{能力 / Profile / Operation}
基线：{source_commit / ledger_commit}
证据：{源码符号、命令、Evidence/Snapshot}
限制：{平台、Provider、未覆盖路径}
下一步：{解除 blocker 的最小动作}
检查重点

结论词必须与证据强度匹配。

对象和基线防止把局部结果外推。

证据要能由下一位评审者复跑。

限制不是附注，而是结论的一部分。

下一步必须直接解除已知 blocker。
