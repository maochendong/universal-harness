00 · RETRIEVAL FIRST

先从上一课恢复权威方向

  1. materializer 应读取所有磁盘文件，还是只读取 committed manifest 引用的内容？
  2. 如果 SQLite 可重建，它能否新增一条 Ledger 中不存在的边？
  3. 尝试用一句话区分“设计由代码落地”和“任务负责兑现需求”。

本课只需记住

  • 关系的身份 = 业务断言 + source 类型 + target 类型 + 方向。
  • 相同节点之间也可能有不同关系，因为它们回答不同审计问题。
  • 投影前必须做完整性检查，非法边不能进入查询面。

01 · RELATION TAXONOMY

先按业务问题分成五组，再记具体关系

以下全部按 source → target 阅读。第 3、5、7–12 课会在真实调用链中再次使用这些关系，本课负责建立完整词法与判断方法。

1. 血缘与版本

DERIVES_FROM 当前版本源自目标依据；SUPERSEDES 当前修订正式取代旧版本；GENERATED_BY 当前工件由目标 Run/过程生成；RESUMES 当前 Run 接续目标中断 Run。

审计焦点：来源、替代、生产者与恢复前缀。

2. 需求与实现

DECOMPOSES_TO 上层意图拆成需求；ADDRESSES 决策回应需求；SHAPES 决策影响组件形状；REALIZES 代码工件承载组件；IMPLEMENTS 任务兑现需求/决策/设计；SPECIFIES 设计工件精确定义目标要求。

审计焦点：从意图到可执行义务是否断链。

3. 证明与裁决

VERIFIES Test 检验 Requirement/Constraint；EVALUATES EvaluationCase 裁判 Task/Run；SUPPORTS Evidence 支持声称；REFUTES Evidence 否定声称；VIOLATES Finding 指出违反规则；DIAGNOSED_BY Finding 由 RCA 解释。

审计焦点：检查、证据、结论与根因不能混成一个动作。

4. 执行与上下文

EXECUTES Run 执行 Task/Gate/Case；INVOKES Run 调用 Tool；PRODUCES Run/RCA 产出 Evidence/Improvement；CONTAINS 容器拥有成员；DEPENDS_ON Task 依赖 Task；USES_CONTEXT Run 绑定 ContextBundle；CAPTURES Checkpoint 固定 Run/Iteration 状态。

审计焦点：谁做、调用谁、依赖什么、结果归谁。

5. 治理与变更

CONSTRAINED_BY 对象受 Constraint 限制；GOVERNED_BY 生命周期受 Policy 控制；BLOCKS Finding 阻止 Task/Iteration；REQUESTS_APPROVAL_FOR 请求放行精确对象；RESOLVES Approval 闭合请求；APPROVES Approval 放行对象；PROPOSES_CHANGE_TO Improvement 提议改目标；TRIGGERS Finding/Improvement 触发 ImpactSet；MAY_IMPACT 版本化对象可能影响另一对象。

审计焦点：约束、授权、触发与候选影响的边界。

需要逐项查询业务语言与主要审计问题时，使用完整关系表；不要用本节卡片替代端点 Registry。

02 · WHY RELATIONS DO NOT MERGE

近义词不能合并，因为它们的主语、对象与生命周期后果不同

REALIZES

CodeArtifact → Component

回答“哪个代码载体落地了这个设计组件”。它是结构实现映射，可用于从组件反查代码影响面。

≠

IMPLEMENTS

Task → Requirement | Decision | DesignArtifact

回答“哪项受控工作负责兑现义务”。Task 完成状态、Evidence 和 Verdict 会沿这条义务链审查。

合并后会丢失两个关键问题：代码文件存在不代表任务完成；任务完成也不说明哪个代码工件承载组件。Impact 传播方向和风险等级也不同：REALIZES 默认 high、IMPLEMENTS 默认 medium。

RESOLVES

Approval → ApprovalRequest

回答“哪个决定闭合了请求”。reject/defer 同样可以处理请求，所以它不自动表示对象获准。

≠

APPROVES

Approval → versionable object

回答“哪个精确对象 digest 获得放行”。只有 approve 决定才形成此授权语义。

合并后，系统会把“请求已处理”误读为“对象已授权”，reject 也可能错误获得执行权。这正是治理系统必须避免的权限扩大。

其余容易混淆的关系

VERIFIES 是 Test 对规则的检查，SUPPORTS/REFUTES 是 Evidence 对声称的方向性结论；EXECUTES 表示承担执行，INVOKES 表示调用工具；DERIVES_FROM 保留来源，SUPERSEDES 改变当前有效版本；TRIGGERS 表示确定事件启动流程，MAY_IMPACT 只表示候选影响。

03 · SOURCE READING 1

Registry 用合法端点把业务词变成可执行约束

EdgeRecord(type, source, target) → RELATION_COMPATIBILITY → compatible or violation

为什么读这段

单看字符串枚举只能知道“有哪些词”；兼容表才说明每个词允许谁指向谁。

packages/graph/src/integrity.ts · relation compatibility 
{ type: "SHAPES", sources: ["Decision"], targets: ["Component"] },
{ type: "REALIZES", sources: ["CodeArtifact"], targets: ["Component"] },
{ type: "IMPLEMENTS", sources: ["Task"], targets: ["Requirement", "Decision", "DesignArtifact"] },
{ type: "VERIFIES", sources: ["Test"], targets: ["Requirement", "Constraint"] },
{ type: "EVALUATES", sources: ["EvaluationCase"], targets: ["Task", "Run"] },
{ type: "EXECUTES", sources: ["Run"], targets: ["Task", "Gate", "EvaluationCase"] },
{ type: "INVOKES", sources: ["Run"], targets: ["ToolDefinition"] },
读法
每一行都是三元约束：relation、source type 集合、target type 集合。
非合并证据
REALIZES 和 IMPLEMENTS 的 source/target 完全不同；合并会让非法事实通过。
下游
完整性检查读取实际节点类型，逐边验证这张表，而不是相信 producer 的字符串。
证据边界
Registry 证明合法语法；不证明图中必需业务链已经完整存在。

04 · SOURCE READING 2

materializer 在投影前执行四类完整性检查

committed operations → candidates + replay edges → assertGraphIntegrity → SQLite projection

为什么读这段

双图不是“尽量显示”；只要存在悬空边、非法端点、版本倒退或依赖环，整个投影必须 fail closed。

packages/graph/src/integrity.ts · checkGraphIntegrity 
return [
  ...checkDanglingEdges(edges, nodeIds),
  ...checkRelationCompatibility(edges, nodeIds, typeById),
  ...checkVersionMonotonicity(nodes),
  ...checkDependencyCycles(edges),
];
悬空边
source 或 target 不存在，关系无法被审计。
端点兼容
节点存在仍不够，类型必须符合 relation Registry。
版本单调
同一对象的修订不能倒退或产生不可裁决分叉。
依赖无环
执行依赖必须可拓扑排序；否则 DAG 无法调度。
先判断：若一条 APPROVES 边指向 ApprovalRequest，节点都存在、digest 都正确，它能进入投影吗？说明应使用哪个关系。

关系裁决

1. ApprovalDecision=reject 后应保留哪条语义？

2. Task 负责兑现一个 DesignArtifact，应使用？

3. Evidence 增强 Requirement 的可信度，应使用？

脱稿关系审查

  1. 从五个关系家族各抽一条，写出 source → target、业务断言和审计问题。
  2. 解释两组不可合并关系，再自选一组近义关系做同样分析。
  3. 给一条非法边，判断是悬空、端点不兼容、版本还是依赖环问题。
