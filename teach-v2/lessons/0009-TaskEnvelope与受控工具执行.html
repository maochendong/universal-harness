LESSON 0009 · ENVELOPE → GRANT → TOOL

Agent 不能靠“计划要做”给自己授权

TaskEnvelope 固定任务身份与执行边界，CapabilityGrant 是治理层签发的可用能力，Tool invoker 在真正副作用前再次校验。三层分开，才能阻止模型输出越过确定性控制面。

Accepted Plan→TaskEnvelope→CapabilityGrant→Tool Invocation→Evidence
本课唯一胜利你能从一次 tool call 反查 TaskEnvelope、Grant 与 Approval，并指出任一缺失时为何必须在副作用前失败。

00 · RETRIEVAL FIRST

先恢复治理不变量

  1. Policy merge 为什么不能 last-write-wins？
  2. Approval 绑定哪四组会漂移的输入？
  3. 如果模型在响应中要求一个未获准工具，谁拥有最终裁决权？

本课只需记住

  • Envelope 固定“这项任务可读、拟写、可用工具和循环策略”。
  • Grant 只能由控制面签发并继续收窄。
  • Invoker 在副作用前检查定义、参数、Grant、Approval 与 intent。

01 · PRODUCTION CALL CHAIN

执行边界由三个不同对象共同成立

Task
accepted obligation
TaskEnvelope
immutable execution input
CapabilityGrant
effective permission
ToolInvoker
pre-side-effect checks
Intent / Result
reconcile + evidence

Envelope 描述任务允许的执行形状，不等于授予能力；Grant 描述当前授权，不等于调用已经发生；Run 通过 INVOKES 连接 ToolDefinition，通过 EXECUTES 连接 Task，通过 USES_CONTEXT 固定 ContextBundle，最后 PRODUCES Evidence。

为什么不把 Grant 直接塞进模型 Prompt

Prompt 是模型可见输入，不是强制边界。即使模型“承诺”只调用某些工具，真正的 ToolInvoker 仍必须基于类型化 Grant 独立校验；否则提示注入或模型错误会变成权限升级。

02 · SOURCE READING 1

TaskEnvelope 先规范化，再计算 digest 和校验结构

Task + plan/context/tool bindings → buildTaskEnvelope → immutable digest

为什么读这段

相同语义输入必须产生相同 envelope；路径重复、顺序差异不能制造不同 digest 或绕过比较。

packages/runtime/src/loop/task-envelope.ts · buildTaskEnvelope 
const normalized: TaskEnvelopeSpec = {
  ...spec,
  allowed_read_paths: [...new Set(spec.allowed_read_paths.map(normalizeRepoRelativePath))].sort(),
  proposed_write_paths: [
    ...new Set(spec.proposed_write_paths.map(normalizeRepoRelativePath)),
  ].sort(),
  tools: [...spec.tools].sort((left, right) =>
    left.name < right.name ? -1 : left.name > right.name ? 1 : 0,
  ),
};
const envelope: TaskEnvelope = { ...normalized, digest: envelopeDigest(normalized) };
规范化路径
转成仓库相对路径、去重、排序，使比较不受输入表示和数组顺序影响。
规范化工具
按 name 排序，避免同一授权集合产生不同 digest。
digest 角色
把任务、计划、上下文、工具与 loop policy 绑定成可校验身份，供 checkpoint/resume 检测漂移。
证据边界
Envelope 合法只证明执行输入结构成立，不证明 Grant 允许其中每项动作。

03 · SOURCE READING 2

ToolInvoker 把 Grant 变成真正的副作用前守卫

ToolDefinition + request + Grant → checkGrant → invoke or ToolError

为什么读这段

权限检查必须紧贴真实调用点。只在 planner 或 UI 检查，会留下其他入口绕过的可能。

packages/runtime/src/tools/invocation.ts · checkGrant 
const action: PolicyAction = {
  kind: "invoke_tool",
  actor: "harness",
  actor_kind: "harness",
  origin: "control_plane",
  phase: request.phase,
  resource: definition.name,
  parameters: request.parameters,
  risk: definition.risk,
};
const reason = grantDenialReason(grant, action);
if (reason !== undefined) {
  throw new ToolError("grant_violation", `invocation of ${definition.name} denied: ${reason}`);
}
重建 PolicyAction
Invoker 不信任调用者给一个“allowed=true”，而从受控 ToolDefinition 和 request 重建动作。
检查维度
phase、resource、parameters 与 risk 一起进入 Grant 裁决，不只是工具名白名单。
失败语义
任何 denial reason 变成 grant_violation，发生在 provider/tool handler 前。
其他守卫
同一调用链还会检查参数 bounds、Approval 和 action intent；Grant 通过不是最终全部通过。
先判断：Envelope 列出了 shell 工具，但 Grant 只允许 read_file。模型发起 shell 时应该由哪一层拒绝？Envelope 是否需要被修改？

即时判断

1. TaskEnvelope 包含一个工具是否等于已经授权？

2. Grant 检查为何放在 ToolInvoker？

3. Run 与 ToolDefinition 之间使用哪条关系？

工具调用审查

  1. 为一条 tool request 标出 Envelope、Grant、Approval 与 Intent 的精确输入。
  2. 指出每层拒绝发生在副作用前还是后，并写出错误类型。
  3. 解释测试通过仍不能证明的外部 Tool/OS 边界。
