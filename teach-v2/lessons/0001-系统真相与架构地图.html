系统真相：Schema、运行图与权威存储

本课不从 CLI 功能清单出发，而从三个架构问题出发：系统允许表达什么事实、一次 Operation 实际物化哪些能力、多个存储副本冲突时谁有裁决权。

本课设计命题

如何让“系统支持某种能力”成为一个可由类型、编译产物和权威记录共同验证的命题，而不是文档中的愿景？

词表封闭

Node、Edge、Event 的类型由 Schema 枚举；调用者不能用自由文本扩展业务语义。

能力零残留

未激活模块不得产生节点、Binding、Checkpoint 或可调用入口。

权威单向

Ledger 可以物化 Projection 和观察层；后两者不能反向改写权威历史。

目标设计

Graph 是工程事实模型，CapabilityPlan 是本次运行授权，Ledger 是完成裁决的唯一权威。

当前实现 · 仓库内已连通

01 · 类型系统就是业务边界

Graph 不是任意关系图：Edge 本身也是受治理的事实

Node 表达工程对象；Edge 不只是两个 id 的连线，还携带关系类型、生命周期状态、来源、血缘、置信度和内容摘要。因此关系可以被提议、接受、拒绝和取代，也能参与审计与漂移检查。

核心源码 1 · Edge 持久化契约
调用者与输入

Graph 写入、反序列化与验证边界提交一个候选 Edge record。

输出与消费者

通过 Schema 的 EdgeRecord 才能进入图存储、传播和治理逻辑。

守卫与失败语义

未知关系/状态、越界 confidence 或缺失 provenance 均在结构边界拒绝。

证据边界

证明持久化形状受约束；不证明某条具体 Edge 已被接受或已进入生产数据。

逐段读法
  1. EDGE_STATUSES 把关系生命周期收敛成四种法定状态。
  2. strictObject 禁止调用者塞入未声明字段，避免旁路业务契约。
  3. type/source_id/target_id 固定关系语义与方向；方向不能靠展示层猜。
  4. source + provenance + digest 让关系可归属、可重放、可检查漂移。
  5. confidence 只接受 0–1；它表达证据强度，不授予接受状态。
关系类型怎样读成业务语义
REALIZES：代码工件落地一个设计组件，连接“结构定义”与“实现载体”。
IMPLEMENTS：执行任务兑现需求、决策或设计义务，连接“工作”与“承诺”。
RESOLVES：批准决定结束批准请求，表达请求生命周期已经闭合。
APPROVES：批准记录放行某对象的精确版本，表达被授权对象及摘要。

为什么不能合并：REALIZES 与 IMPLEMENTS 的 source kind、审计问题和影响传播方向不同；RESOLVES 闭合请求，APPROVES 授权对象版本。合并会丢失“处理了哪个流程”与“放行了哪个对象”的独立证据。 查看全部 32 种 Relation Type 的业务语言 →

02 · 编译产物决定可调用面

CapabilityPlan 不是配置快照，而是一次 Operation 的运行授权

全量架构只说明系统可能拥有什么。编译器先解析 active capability set，再由 buildOperationDag() 物化当前 Operation 的节点和数据依赖。

核心源码 2 · 活动能力物化
调用者

Capability compiler 将解析后的 active set 交给 DAG builder。

产物

返回有顺序依赖、消费 Binding 与产出 Binding 的节点数组。

关键不变量

Impact/Design 只有 active 时存在；Plan 的依赖和输入随之同步扩展。

不能推断

能构图不等于节点已运行；运行事实仍要看 journal、Event 与 Ledger Evidence。

逻辑块讲解
  1. 函数签名只接收 active set，输出因此可确定性重建。
  2. Capture 与 capability_decision 是固定 Kernel 脊柱。
  3. 条件分支同时决定模块节点是否存在，未激活能力没有“空壳 Port”。
  4. Impact 激活时，Plan 既新增执行依赖，也新增 impact_set 数据依赖。
  5. 控制依赖与数据依赖一起变化，避免“顺序到了但输入并不存在”。

03 · 权威与策略不可混为一层

Ledger 裁决事实；传播规则裁决影响如何扩散

1

Git-native Ledger

append-only、可验证、可重放；批准、Evidence 与 Snapshot 的权威来源。

2

SQLite Projection

从 Ledger 物化的查询缓存；漂移时删除并确定性重建。

3

Live Spool

heartbeat、阶段与输出摘要等可删除运行观察；不授予“已完成”。

核心源码 3 · 影响传播策略表
调用者

Impact traversal 读取 Edge type，再查询该类型的传播政策。

产物

返回方向、默认风险与是否允许 inferred edge 继续传播。

守卫

高风险否定关系拒绝推理传播；政策写在代码表中，不交给模型临场决定。

不能推断

规则只定义传播语义；某次 ImpactSet 是否接受仍需运行与 Ledger 证据。

逻辑块讲解
  1. 每种可传播关系必须显式登记，未知关系不会获得默认扩散权。
  2. 否定与阻断只向 source→target 传播，且拒绝低置信推理边。
  3. VERIFIES 双向可查，ADDRESSES 逆向回溯，反映不同审计问题。
  4. SPECIFIES 可双向定位契约与对象，但不允许 inferred edge 扩大高风险影响。
