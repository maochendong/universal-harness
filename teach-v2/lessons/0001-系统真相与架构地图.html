LESSON 0001 · GLOBAL MODEL

先看懂整台机器：系统真相与架构地图

本课不钻某个函数。先回答三个根问题：系统为什么存在、一次迭代怎样流动、谁有资格宣布“完成”。后面所有源码细节都必须能放回这张地图。

全局系统→ 编译运行图→ 验收追踪→ 模型连通→ 治理与发布
本课唯一胜利你能不看页面，画出“事实与意图 → 编译 → 执行 → 裁决 → Ledger”的主链，并正确解释 Kernel 与 Module 的区别。

01 · SYSTEM PURPOSE

它不是“让 Agent 写代码”，而是“让迭代可审计”

普通 Agent Loop 关心下一步做什么；Universal Harness 还要回答：为什么允许做、依据是什么、失败如何阻断、完成由什么证据证明。

Kernel

所有 Profile 都共享的固定生命周期脊柱：Capture → Capability Decision → Plan → Context → Execute → Verify → Snapshot。它控制流程秩序和完成边界。

Module

按 CapabilityPlan 激活的可选子图，例如 Impact、Design、Evaluate、Audit。未激活时，运行图里根本不应出现对应节点。

CapabilityPlan

根据 Profile、风险、Policy 与 Provider 事实编译出的 operation-scoped 运行图。它不是偏好配置，而是本次迭代的能力授权。

Evidence 与 Ledger

Evidence 证明某个声称；Snapshot 汇总完成状态；Git-native Ledger 才是权威事实。Dashboard 与数据库只是投影。

设计不变量

Profile 改变的是被激活的子图，不是复制出另一套 Kernel。因此 Lite、Standard、Governed 必须共享相同的生命周期语义。

02 · THE MAIN CHAIN

一次迭代从意图变成可提交事实

1. 事实与意图
Requirement · Risk · Policy · Provider
2. 编译
ProfileDecision → CapabilityPlan
3. 受控执行
Kernel + activated Modules
4. 裁决
Verify · Evaluate · Verdict
5. 提交
Snapshot → Ledger
模型的地位模型可提出 PRD、Design、Plan 或分析候选；它不直接写入事实层。
确定性层的地位Schema、Compiler、Validator、Policy 与 Evidence 决定候选能否继续。
投影层的地位SQLite、Markdown、Dashboard、Live Spool 帮助查询和观察，但不能反向定义真相。
先做一次架构预测：如果 Dashboard 显示任务成功，但 Ledger 中没有通过的 Verdict 和已提交 Snapshot，你会把哪一边当成事实？为什么？

答案

以 Ledger 为准。Dashboard 是可重建的投影；它可以延迟、过期或来自未提交状态。完成必须回到 Evidence、Verdict 与 Snapshot 的权威链。

03 · TARGET VS CURRENT

目标设计和当前事实要同时看，但不能混写

目标设计

全链路由契约和证据闭环

每个能力都应从声明、Binding、运行消费者一直追到生产 Evidence 和发布环境证明。

当前实现

仓库内主链已成形

核心编译、DAG、严格 TDD 和模型装配有代码与测试；当前外部 Provider 和跨平台闭环仍需单独复验。

因此“当前外部部分连通”不是说接口只有一半。它表示：仓库内生产装配和消费者存在，但当前提交缺少真实外部调用的同强度证据。第 4 课会沿这条链精确拆开。
