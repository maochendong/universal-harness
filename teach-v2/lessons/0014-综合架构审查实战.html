00 · CUMULATIVE RETRIEVAL

先用一张白纸重建整条系统

  1. 画出 Profile → CapabilityPlan → Operation DAG → TaskEnvelope → Tool → Evidence → TaskVerdict → Snapshot → Ledger。
  2. 在旁边补上双图/Impact、Context/Policy/Approval、Checkpoint/Reconcile、Feedback/Promotion、Projection/M3。
  3. 给每个派生面画一条从权威源指向它的单向箭头。

综合审查只需守住五问

  • 声称的对象、Profile、commit 与环境是什么？
  • 谁是权威定义，谁是真正生产消费者？
  • 哪里 fail closed，失败留下什么状态？
  • 哪条命令或 Ledger Evidence 能复跑？
  • 证据明确不能证明什么？

01 · CHOOSE ONE CLAIM

从两个真实争议中选择一个，不要同时做

A · 当前外部 Provider 已连通

待审查声称：“七类模型能力已经从 Profile binding 穿透到真实外部 Provider，并由生产消费者使用。”

主要风险：把 Schema/Adapter/fixture tests 当真实网络与凭据证据；把历史 dogfood 外推到当前 commit。

起始课：02、04、08、11。

B · M3 远程协作已完成

待审查声称：“多个 Replica 已能通过 Coordinator 安全 Lease、远程批准并 CAS 集成到 Target。”

主要风险：把 Protocol records、Port 或 connect slice 当完整 Lease/Approval/Integration 闭环。

起始课：05、08、10、13。

禁止模糊改题：不能把 A 改成“仓库里有 Provider 代码”，也不能把 B 改成“有 M3 设计”。你要裁决原声称，再按证据范围降级结论。

02 · REVIEW WORKSHEET

按七步写，任何一步缺证据都保留为 gap

1. Scope

写能力、Profile、source commit、worktree 是否干净、外部环境与时间。

2. Target design

用设计文档写预期链和不变量，但标记“目标”，不先判实现。

3. Authority

找 Schema/Registry/Compiler/Ledger；说明哪个对象有最终裁决权。

4. Production chain

从真实入口追到 Coordinator/Runner/Invoker/consumer，拒绝停在 interface。

5. Failure semantics

至少找一个 drift、coverage、authorization 或 CAS 守卫，并写失败后的状态。

6. Evidence

先 targeted tests，再按声称运行 E2E、真实 provider 或 remote host 验证。

7. Verdict

只用 passed / partial / not_verified / blocked，并把限制写进结论正文。

03 · SOURCE MAP WITH READING PURPOSE

源码入口按审查问题组织，不按目录顺序罗列

问题 Provider 声称 M3 声称 读它为了判断什么
契约能否表达 profile.ts collaboration.ts 字段、digest 与状态词表是否封闭；只能证明定义存在。
生产 seam 在哪里 managed-pipeline-ports.ts collaboration/port.ts 调用者依赖的深模块是什么；Port 本身仍不能证明实现覆盖。
谁真正执行 managed-runner.ts collaboration/coordinator.ts 沿函数分支确认当前真实 consumer、未实现 command 与 fail-closed 路径。
谁接受事实 task-verdict.ts ledger/repository.ts 结果如何进入 Verdict/Ledger；外部响应或 projection 不能自行变成事实。
现有外部证据 T20 dogfood M3 design 前者是历史真实调用，后者只是目标设计；两者证据类型完全不同。
如何读一段未完成源码

先看它在当前 Git commit 还是 dirty worktree；再找调用者、typed outcome、明确未实现分支与测试。未完成不是“没有价值”，但结论必须写“已实现到哪一条 slice、下一条缺口是什么”。

04 · EVIDENCE PACK

先保存基线，再运行所选声称的证据包

Architecture review evidence pack

git rev-parse HEAD && git status --short && pnpm exec vitest run packages/runtime/test/model/managed-runner.test.ts packages/cli/test/managed-pipeline-ports.test.ts packages/core/test/collaboration/records.test.ts packages/runtime/test/collaboration/coordinator.test.ts packages/core/test/ledger/repository.test.ts

证据边界：这个合并包只建立当前 source/worktree 与仓库内测试状态。选择 A 仍需当前真实 Provider 调用；选择 B 仍需完整 commands、真实平台权限、protected Control Ref、Lease 与 Target CAS 的同 commit E2E。

最终裁决校准

1. 历史真实 Provider dogfood 能否证明当前 commit 外部连通？

2. M3 connect slice 通过但 Integration 未实现，最佳结论是？

3. 哪项最能证明你掌握了课程？

05 · COURSE COMPLETION RUBRIC

达到 Review 级掌握，才记录课程完成

  1. 全局：不看资料画出主链与权威/投影方向。
  2. 源码：对所选声称解释至少两个核心函数的 caller、input/output、guard 与 failure。
  3. 关系：正确使用至少六种 relation，并解释其中一组为何不能合并。
  4. 证据：保存 commit、worktree、命令和结果，明确测试不能外推的环境。
  5. 结论：给出范围化 verdict、blocker 与解除 blocker 的最小下一步。
声称：{精确可判定句}
结论：{passed | partial | not_verified | blocked}
基线：{HEAD + worktree + environment}
生产链：{entry → consumer → authority}
关键守卫：{symbol + failure state}
证据：{tests + Ledger/external evidence}
残余风险：{明确不能证明什么}
下一步：{解除最关键 blocker 的最小动作}

学习记录规则：完成上述输出后再把真实回答与误区写入 learning-records/。页面访问、测验点击和“我已复跑”按钮都只是本地导航状态，不自动生成掌握结论。
