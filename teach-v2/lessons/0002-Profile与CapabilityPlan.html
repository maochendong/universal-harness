LESSON 0002 · COMPILER CONTRACT

Profile 如何被编译成可执行的 CapabilityPlan

本课从编译器设计而不是 Profile 使用方式出发：给定 Profile、风险、Policy 与 Provider，追踪能力解析、依赖闭包、Provider 闭包、修订状态和 runtime guard 如何共同决定可执行面。

本课设计命题

如何在编译期决定“哪些能力有权存在”，并确保 provisional 决策、缺失 Provider 或摘要漂移无法偷渡到 Plan 阶段？

确定输入

Profile、Risk、Policy、baseline 与 Provider 都以摘要绑定到修订。

闭包完整

active capability 必须带齐依赖和 required Provider，否则编译失败。

Final 才授权

仍有 deferred 的 provisional 只能记录决策，不能进入 Plan runner。

目标设计

一个 Kernel，按需编译能力

Lite、Standard、Governed 不分叉成三套代码；它们通过能力解析、依赖闭包和 Provider 闭包生成不同的 DAG。

当前真实实现

编译、物化、路由均有测试

05871fc 上，Capability 编译与 runtime 路由的指定测试为 31/31。这证明仓库内链路，不等于声称某个外部 Provider 环境已可用。

架构审查结论

ProfileDefinition 是协议默认值，ProfileDecision 是项目选择，CapabilityPlan 才是 operation-scoped 编译产物；三者不能共享一个“配置”概念，否则无法表达修订与授权边界。

读图约定

Lite 展示完整默认脊柱；Standard 与 Governed 只突出档位增加的能力节点。完整 Kernel 仍包含 capture → capability_decision → plan → context → execute → verify → snapshot。

Lite5 项均为 conditional
Capture→ Decision→ Plan→ Context→ Execute→ Verify→ Snapshot

默认只有 Kernel 脊柱。若激活 strict_tdd，依赖闭包会连带激活 design_governance 和 impact_analysis。

StandardImpact / Design / Evaluate 必需
Capture→ Impact→ Design→ Plan→ Execute + TDD→ Evaluate→ Snapshot

strict_tdd 是唯一法定 deferred 点：默认在 provisional 等待已接受的 DesignSet，然后在 final 修订中绑定测试策略。上图表示未被 Policy 禁止时的最终图。

Governed5 项能力均必需
Impact→ Design→ Execute + TDD→ Evaluate→ Snapshot→ Audit

全部模块物化。strict_tdd 还要求 isolated_workspace_provider 和 structured_gate_provider；缺任何一个都在编译时 fail closed。

协议默认值 definitions.ts:43–65

编译器读取 Lite/Standard/Governed 的 capability resolution 默认值；输出不是 DAG，也不授予执行权。审查重点是档位差异是否只表现为数据。

调用者

真实源码 · 原样 9 行

Final guard 把意图变成执行边界

packages/core/src/capability/compiler.ts:611–619
CODE 
export function assertCapabilityPlanFinal(plan: CapabilityPlanRecord): void {
  const deferred = plan.capabilities.filter((entry) => entry.resolution === "deferred");
  if (plan.compilation_stage !== "final" || deferred.length > 0) {
    throw new CapabilityCompileError(
      "plan_not_final",
      `capability plan revision ${plan.revision} is ${plan.compilation_stage}; only a final plan may enter plan`,
    );
  }
}
中文翻译

这个函数只做一件事：判断这张运行图是否有权进入 Plan。

它先找出仍未解析的能力；“暂时不知道”不能被当成“默认关闭”。

只要修订还不是 final，或者仍有 deferred，条件就失败。

失败不降级，而是抛出类型化的 plan_not_final。

结果：暂定决策可以被记录和完善，但不能偷渡成执行授权。

双层守卫

编译器会拒绝没有 provisional 血缘、没有已接受 DesignSet、输入漂移或缺 Provider 的 final 修订；capability-dag-runtime.ts:76–100 又在 Plan runner 前调用这个 final guard。

核心源码 2 · Runtime 二次授权检查
调用者与输入

WorkflowDagEngine 即将执行 Plan 节点时调用包装后的 runner，并闭包捕获当前 CapabilityPlan。

下游

final 时委托真实 planRunner(context)；否则返回标准 blocked outcome。

失败语义

异常不会退回 legacy 路径，而被翻译为 capability_plan_not_final。

不能推断

守卫通过只授权进入 Plan；它不证明节点完成或 Snapshot 已提交。

逻辑块讲解
  1. 先保存原始 Plan runner，避免覆盖依赖注册。
  2. 只包装 Kernel 的 plan 槽位，其他 runner 保持原状。
  3. 每次真正调用 Plan 前重新校验，防止调用者绕开编译阶段。
  4. 所有 final-check 失败被收敛成稳定的 blocked reason，供 DAG engine 和证据层消费。
