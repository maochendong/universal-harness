LESSON 0002 · PROFILE → RUNTIME

Profile 如何变成一张真正可执行的运行图

Profile 不是三套流程的开关，也不是直接执行的配置。它只是编译输入之一；Capability compiler 结合风险、Policy 与 Provider 事实，产出本次 operation 的 CapabilityPlan 和 DAG。

全局系统→编译运行图→验收追踪→模型连通→治理与发布
本课唯一胜利你能解释为什么 inactive Module 在 DAG 中必须“完全不存在”，以及为什么 provisional CapabilityPlan 即使已生成也不能进入 Plan runner。

本课只需记住

  • Profile 是编译输入，CapabilityPlan 是 operation 级授权结果。
  • inactive Module 在 DAG 中物理不存在，不产生空壳节点。
  • Runtime 在执行前重验 final plan，provisional/deferred 必须 fail closed。

01 · DESIGN PROBLEM

一个 Kernel，如何安全承载不同治理强度？

如果为 Lite、Standard、Governed 各写一套 orchestrator，生命周期语义会分叉；如果只在运行时到处判断开关，又无法审计本次到底授权了什么。

ProfileDefinition协议注册的默认能力解析，不是运行实例。
ProfileDecision项目对档位和输入事实的已记录选择。
CapabilityPlan针对某次 operation 编译出的授权与运行图。

关键设计

变化被收敛进“编译结果”，Kernel 本身保持稳定。这样运行时只执行一张明确 DAG，而不是重新解释 Profile 意图。

03 · SOURCE READING 1

DAG builder 把“inactive”实现成“物理不存在”

调用链位置：CapabilityPlan active set → buildOperationDag → OperationDagNode[]

为什么读这段

它直接回答 Profile 是否复制流程：固定 Kernel 节点总会创建，可选 Module 只有 active 时才被 push。

packages/core/src/capability/dag.ts · buildOperationDag 
export function buildOperationDag(active: ReadonlySet<CapabilityId>): OperationDagNode[] {
  const nodes: OperationDagNode[] = [
    kernelNode("capture", [], [], ["requirement_baseline"]),
    kernelNode("capability_decision", ["capture"], ["requirement_baseline"], []),
  ];
  if (active.has("impact_analysis")) {
    nodes.push(moduleNode("impact_analysis", "impact", ["capability_decision"]));
  }
谁调用、输入是什么
Capability compiler 得到 active capability 集合后调用；输入不是原始 Profile，而是已经过 Policy、依赖与 Provider 闭包解析的结果。
输出交给谁
返回 OperationDagNode 列表，随后进入 CapabilityPlan，并由 runtime DAG engine 消费。
关键逻辑
capture 与 capability_decision 属于固定 Kernel；impact 只在 active set 包含对应 capability 时物化。
失败与证据边界
这个 builder 本身不判断 plan 是否 final；它证明结构物化规则，不证明 runtime 已经执行该图。
阅读源码 2 前先预测：假设调用者拿到一张 compilation_stage="provisional" 且仍含 deferred capability 的 DAG，直接请求执行 Plan。runtime 应该继续、降级到旧流程，还是返回 blocked？请先写下理由。

04 · SOURCE READING 2

Runtime 在最后一刻重新检查授权

调用链位置：WorkflowDagEngine → guarded Plan runner → real planRunner

为什么还要第二道守卫

即使编译器已经校验，runtime 也不能信任调用者一定走过正确路径；执行边界必须自行 fail closed。

packages/runtime/src/orchestration/capability-dag-runtime.ts · guarded plan runner 
plan: (context) => {
  try {
    assertCapabilityPlanFinal(plan);
  } catch {
    return {
      status: "blocked",
      reason: "capability_plan_not_final",
      detail: "a provisional or deferred CapabilityPlan cannot enter Plan",
    };
  }
调用者与闭包输入
DAG engine 调用包装后的 Plan runner；包装器闭包持有当前 CapabilityPlan，同时接收运行上下文。
守卫强制什么
assertCapabilityPlanFinal 要求 compilation stage 为 final 且没有 deferred capability。
失败语义
失败被翻译成稳定的 blocked outcome，不降级、不绕行，也不会调用真实 planRunner。
下游和证据边界
只有通过守卫才委托 Plan。通过只表示“允许进入”，不表示 Plan、Execute 或 Snapshot 已完成。

本课结论

Profile 提供默认解析，Compiler 生成授权事实，DAG builder 物化结构，Runtime guard 执行最终边界。四层各自承担不同责任，不能压成一个“配置开关”。
