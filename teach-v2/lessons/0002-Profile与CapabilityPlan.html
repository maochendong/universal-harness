LESSON 0002 · ONE CONCEPT

Profile 不是流水线，而是一张运行图的编译输入

你要获得的能力只有一个：给定 Profile、风险、Policy 与 Provider，预测哪些节点会存在，以及运行会在哪里被阻断。

目标设计

一个 Kernel，按需编译能力

Lite、Standard、Governed 不分叉成三套代码；它们通过能力解析、依赖闭包和 Provider 闭包生成不同的 DAG。

当前真实实现

编译、物化、路由均有测试

05871fc 上，Capability 编译与 runtime 路由的指定测试为 31/31。这证明仓库内链路，不等于声称某个外部 Provider 环境已可用。

AHA

Profile 像舞台剧本的版本：它不亲自演出，而是决定哪些角色上场、谁必须等谁，以及开演前必须检查哪些设备。

读图约定

Lite 展示完整默认脊柱；Standard 与 Governed 只突出档位增加的能力节点。完整 Kernel 仍包含 capture → capability_decision → plan → context → execute → verify → snapshot。

真实源码 · 原样 9 行

Final guard 把意图变成执行边界

packages/core/src/capability/compiler.ts:611–619
CODE 
export function assertCapabilityPlanFinal(plan: CapabilityPlanRecord): void {
  const deferred = plan.capabilities.filter((entry) => entry.resolution === "deferred");
  if (plan.compilation_stage !== "final" || deferred.length > 0) {
    throw new CapabilityCompileError(
      "plan_not_final",
      `capability plan revision ${plan.revision} is ${plan.compilation_stage}; only a final plan may enter plan`,
    );
  }
}
中文翻译

这个函数只做一件事：判断这张运行图是否有权进入 Plan。

它先找出仍未解析的能力；“暂时不知道”不能被当成“默认关闭”。

只要修订还不是 final，或者仍有 deferred，条件就失败。

失败不降级，而是抛出类型化的 plan_not_final。

结果：暂定决策可以被记录和完善，但不能偷渡成执行授权。

双层守卫

编译器会拒绝没有 provisional 血缘、没有已接受 DesignSet、输入漂移或缺 Provider 的 final 修订；capability-dag-runtime.ts:76–100 又在 Plan runner 前调用这个 final guard。

05 · 检索练习

不看上文，做三次架构判断

这些题测的不是文件名记忆，而是你能否预测新场景中的图和失败边界。

1. Standard 的 provisional 修订仍有 deferred，但团队希望开始 Plan。系统应该怎样处理？

2. Lite 通过合法风险激活启用 strict_tdd，并且所需 Provider 齐全。哪个图变化正确？

3. Standard 有已接受 DesignSet，但 final 请求没有指向 provisional 修订。哪个结果符合 fail-closed？

完成标准

你能用一份 CapabilityPlan JSON 回答四个问题

  1. 每项能力是 active、inactive 还是 deferred，根据来自哪里？
  2. 依赖闭包额外拉入了什么？
  3. 哪些 Operation DAG 节点实际存在？
  4. 它现在是否有权进入 Plan，证据是什么？
