LESSON 0004 · PORT → CONSUMER

怎样证明一个模型 Provider 真的“连通”

有接口、有 Adapter、甚至测试全绿，都不等于当前外部 Provider 已经真实调用。技术判断必须把 Port 契约、精确 Binding、生产装配、运行消费者和外部 Evidence 分层检查。

全局系统→编译运行图→验收追踪→模型连通→治理与发布
本课唯一胜利看到“Provider 已接入”时，你能沿五层链逐项找证据，并准确解释为什么当前仓库内是已连通、当前外部仍只能标记部分连通。

00 · RETRIEVAL FIRST

先从验收链恢复证据边界

  1. 一个接口存在能否证明生产消费者已经调用它？
  2. targeted tests 全绿能否证明真实凭据和网络可用？
  3. 模型输出通过 Schema 后，是否自动成为 accepted fact？

本课只需记住

  • 连通要穿过 Port、Binding、Resolver/Adapter、Runner/Validator 与 Consumer。
  • 仓库内接线和当前外部验证必须分别定级。
  • required provider closure 不完整时，生产装配必须整体失败。

01 · DESIGN PROBLEM

模型只能提议；确定性边界必须握住裁决权

同一个模型调用会受 Provider 身份、配置、Prompt contract、输出 Schema、预算和失败模式影响。如果只保存“用了哪个模型”，重放时无法证明得到的是同一种候选，也无法安全验证输出。

Port

业务阶段所需的抽象能力，例如 design proposal 或 feedback analysis。它说明“要什么”，不说明由谁提供。

Binding

把 Port 精确绑定到 Provider、配置摘要、Prompt contract、输出 Schema、预算和失败模式，是可审计的运行输入。

Resolver / Adapter / Runner

Resolver 根据 Binding 找 Provider；Adapter 翻译业务输入输出；managed runner 校验 Binding 漂移并执行调用。

Validator / Consumer

确定性 Validator 拒绝不合 Schema 的候选；真正的生产消费者把通过的候选交给后续协调器，而不是直接写成事实。

02 · PRODUCTION CALL CHAIN

“连通”至少要穿过五个接缝

Port
required business capability
Binding
provider + prompt + schema
Resolver / Adapter
production assembly
Runner / Validator
invoke + fail closed
Consumer / Evidence
accepted candidate + proof

当前代码已经存在 CLI 生产装配、managed runner、Provider registry 与多个生产消费者；相应仓库内测试可复跑。但当前提交没有新的真实外部 DeepSeek 调用证据，因此不能把“仓库内链路已连通”外推为“当前外部环境已验证”。

状态翻译

当前仓库：已连通。接口、装配、runner、validator、consumer 与 targeted tests 存在。当前外部：部分连通。历史真实调用存在，但当前提交/环境未复验真实 Provider，跨平台 AC25 也未完成。

03 · SOURCE READING 1

Binding 固定的是完整调用契约，不只是 Provider 名字

调用链位置：CapabilityPlan / Profile data → ModelProviderBindingSchema → Resolver

为什么读这段

它定义了可重放和防漂移所需的最小身份：Provider、配置、Prompt contract、输出 Schema、预算与失败模式必须一起固定。

packages/core/src/schema/profile.ts · ModelProviderBindingSchema 
export const ModelProviderBindingSchema = strictObject({
  slot_id: enumerated(MODEL_SLOT_IDS),
  purpose: Type.Optional(enumerated(GROUNDED_SYNTHESIS_PURPOSES)),
  required: Type.Boolean(),
  provider_identity: Type.String({ minLength: 1 }),
  config_digest: DigestSchema,
  prompt_version: Type.String({ minLength: 1 }),
  prompt_contract_id: Type.String({ minLength: 1 }),
  prompt_contract_version: Type.String({ minLength: 1 }),
  prompt_contract_digest: DigestSchema,
  output_schema_digest: DigestSchema,
  schema_version: Type.String({ minLength: 1 }),
  budget_profile: Type.String({ minLength: 1 }),
  failure_mode: enumerated(MODEL_BINDING_FAILURE_MODES),
});
谁生产、谁消费
Compiler 从 PromptContractRegistry 与 Provider 配置解析 Binding；Resolver 和 managed runner 在生产装配与调用时消费。
前三组字段
slot_id/purpose/required 描述业务槽位；provider_identity/config_digest 固定实现；Prompt contract 四字段固定提示协议身份。
输出与失败策略
output_schema_digest 固定可接受结构，budget_profile 限制资源，failure_mode 决定缺失或调用失败是否阻塞。
证据边界
Schema 存在只证明 Binding 形状被定义；它不证明所有 required Port 都已解析，也不证明 Provider 已被真实调用。
阅读源码 2 前先预测：如果 Profile 要求七个阻塞型模型槽位，Resolver 只解析出六个，生产装配应降级到 deterministic fallback，还是在 preflight 阶段整体失败？

04 · SOURCE READING 2

生产装配重新验证 required Provider closure

调用链位置：required slot keys + Resolver results → coverage guard → managed pipeline ports

为什么读这段

它把“required”从声明变成生产前置条件：任何必需槽位没有解析结果，整个 managed ports 装配都会失败。

packages/cli/src/managed-pipeline-ports.ts · required slot coverage 
const uncovered = requiredSlotKeys.filter((key) => resolvedByKey[key] === undefined);
if (uncovered.length > 0) {
  throw new ManagedPipelinePortsError(deps.profile_id, uncovered);
}
上游输入
requiredSlotKeys 来自 Profile 的必需模型槽位；resolvedByKey 汇总 design、impact、plan、context、narrative、feedback 等 Resolver 结果。
关键逻辑
筛出没有解析结果的 required key。只要有一个 uncovered，装配就抛出带 profile 与缺口列表的类型化错误。
失败语义
阻塞型槽位不会静默降级到 legacy/deterministic path，从而避免 CapabilityPlan 声称模型存在、实际却走另一条路径。
下游与证据边界
通过后才创建 adapters 并交给 pipeline consumers。这个 guard 证明装配闭包完整，仍不等于网络、凭据和外部服务当前可用。
定义存在Port、Schema、Adapter 能被定位。
仓库连通生产装配、消费者与测试形成闭环。
外部验证当前提交真实调用、凭据环境和发布证据齐备。
