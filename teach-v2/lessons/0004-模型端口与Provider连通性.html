第 4 课 · PORT / BINDING / RUNTIME · 约 35 分钟

模型端口如何获得生产调用资格

本课审查从领域 Port 到外部 Provider 的完整责任链。目标不是学会“配置一个模型”，而是理解谁定义能力、谁钉住版本、谁装配实现、谁验证输出，以及什么证据才足以宣称连通。

本课设计命题

如何允许模型生成受限候选，同时确保 Provider、Prompt、Schema、预算、失败模式和最终领域裁决都不能在调用途中静默漂移？

能力与实现分离

Port 定义领域能力；Provider 只实现调用，不拥有 Graph 写入权或裁决权。

Binding 精确

slot、purpose、Provider、Prompt Contract 与 output Schema 必须以 digest 共同绑定。

Required 不降级

blocking slot 缺覆盖、Binding 漂移或校验失败时必须 typed block。

目标设计

CapabilityPlan 携带可审计 Binding，Managed Runner 执行精确版本，Validator 只将合格候选交给领域消费者。

当前实现 · 双维度

仓库内生产链已连通；当前外部 Provider 部分连通。本页后续分别给出源码、测试和证据范围。

“当前外部部分连通”是什么意思：历史提交已有真实端点调用证据，所以不能判为“未连通”；但课程基线所在当前环境没有 DeepSeek 密钥，当前提交未重新产生真实 Provider Evidence，所以也不能判为“已连通”。该状态只描述外部复验，不否定仓库内 Adapter、Runner、Validator 与生产消费者的接线。

01 · 类型与版本契约

ModelProviderBinding 把一次调用所依赖的全部版本钉在一起

Slot 回答“需要哪类模型能力”，purpose 在复用 Port 时进一步区分业务用途。Binding 负责把抽象能力解析为一个可重放、可检查漂移的调用合同。

核心源码 1 · Binding Schema
调用者与输入

Capability compiler 依据 Profile、Provider registry 与 PromptContractRegistry 生成 Binding；字段不是人工拼装配置。

输出与消费者

ModelProviderBinding 持久化进 CapabilityPlan；runner 侧的调用 Binding 用这些身份与 digest 检查一致性。

守卫

未知 slot/purpose/failure mode、空 identity 和无效 digest 在 Schema 边界拒绝。

不能推断

Binding 合法只证明合同完整；不证明 Provider 可达、输出合格或领域结果被接受。

逻辑块讲解
  1. slot_id + purpose 形成领域能力键；purpose 只在 Grounded Synthesis 复用时出现。
  2. required 与 failure_mode 决定缺失或失败能否继续，而不是由 Adapter 自行降级。
  3. provider_identity + config_digest 钉住实现及非秘密配置版本。
  4. Prompt 的 id、version、contract digest 与 output schema digest 同时保存，区分人类可读版本和机器可验证内容。
  5. budget_profile 也是合同的一部分，防止同一逻辑调用在成本边界上漂移。

02 · 生产装配与当前实现差异

核心源码 2 · Resolver 调用面
调用者与输入

createManagedPipelinePorts() 接收 profile、runtime config、host environment、fetch 与 Provider registry。

输出与下游

每个 resolved Provider 被传给对应 Adapter；返回的 ManagedPipelinePorts 注入 Coordinator 和 DAG runner。

设计约束

Proposal 与 Review 独立解析；Context、Narrative、Feedback 也保留独立 key，避免错误共享失败语义。

证据边界

resolver 返回实现不等于已调用外部端点；调用记录与 Evidence 要在 Managed Runner 后确认。

逐行讲解
  1. Design Proposal 与独立 Review 使用不同 Port key，防止自提自审成为隐式默认。
  2. Impact 与 Plan 各自只产生领域候选，后续确定性校验仍拥有裁决权。
  3. Context 与 Narrative 虽复用 Grounded Synthesis 类型，却因 purpose 和失败模式不同而独立解析。
  4. FeedbackAnalysis 出现在同一生产装配函数中，证明它不再只是孤立 Adapter。
目标链路

CapabilityPlan 的精确 model_provider_bindings 应作为 invocation 的直接授权输入，一路传到 Managed Runner。

当前差异 · 部分直接

compiler 将 Binding 写入 CapabilityPlan；CLI assembly 又从同一 runtime config、host registry 与 Prompt Registry 重新解析 Provider，Adapter 再构造 invocation binding。当前 createManagedPipelinePorts() 调用面没有直接接收 CapabilityPlan Binding 对象。

如何理解这个差异：相同 registry 与 digest guard 降低了漂移风险，preflight 也会重查 required coverage；但源码只能证明“两端使用同源配置并各自校验”，不能声称“同一个持久化 Binding 对象被直接传递到底”。这是实现血缘需要继续收紧的设计缺口，不等于所有生产 Port 未接线。

03 · Fail-closed 与生产消费者

连通必须同时证明“缺失时会停”和“结果确实被消费”

核心源码 3 · Required coverage preflight
调用者

CLI 在返回 pipeline ports 前，对当前 Profile 的 required slot keys 执行覆盖检查。

输出

全部覆盖时继续构造 Adapter；有缺口时抛 ManagedPipelinePortsError。

失败语义

Standard/Governed 的 required blocking slot 不得静默落回 deterministic/legacy path。

不能推断

覆盖只证明可解析 Provider，不证明网络可达、凭据有效或输出通过领域校验。

逻辑块讲解
  1. 先把所有实际 resolver key 映射到解析结果，检查范围与装配范围相同。
  2. requiredSlotKeys 由 Profile 决定，因此 Lite 可保留合法 legacy path，受治理档位不可借用。
  3. filter(undefined) 计算精确缺口列表，错误可以说明哪些 Port 无覆盖。
  4. 异常发生在返回 ports 之前，所以不存在“一半已装配”的可运行对象。
核心源码 4 · FeedbackAnalysis 生产消费点
调用者与输入

DAG registry 用 withFeedbackAnalysis() 包装 Verify/Evaluate/Audit runner；输入是已提交节点结果派生的 Finding request。

输出与下游

Coordinator 返回 analyzed/blocked；可继续原节点结果，也可阻断后续路由或要求人工复核。

顺序不变量

底层 runner 未 committed 时不调用模型；模型 blocked 时外层节点也 blocked。

不能推断

该消费点证明生产接线；当前外部端点是否真实调用仍需 ModelInvocationRecord 与本提交 Evidence。

逐段讲解
  1. 先执行确定性 DAG runner，只有 committed result 才触发反馈分析。
  2. feedback.requests 把节点结果转换成领域请求，模型不直接读取任意上下文。
  3. Coordinator 拥有分析状态机与验证逻辑；Provider 只是内部依赖。
  4. required 分析失败时，wrapper 把失败提升为节点 blocked，防止“模型失败但流程照常成功”。

04 · 状态矩阵与证据边界

一个“已接入”声称必须拆成四个问题

审查维度 当前判定 证据 不能外推
契约与 Adapter 已连通 Binding Schema、Prompt registry、领域 Adapter 与 validator 存在并有测试。 不证明进入生产消费者。
生产装配与消费 已连通 CLI resolver、preflight、DAG/Coordinator 消费点与接线测试。 不证明当前外部端点可达。
当前外部 Provider 部分连通 有历史真实调用；当前环境无 DeepSeek key，本提交记录为 not_verified。 不允许声称当前提交已复验。
跨平台发布 部分连通 本地 release 门禁运行；AC25 缺同 commit 三平台聚合工件。 不允许声称 Protocol 1.1 已通过发布验收。
