LESSON 0012 · FINDING → RCA → IMPROVEMENT → PROMOTION

系统可以提出改进，但不能偷偷改写自己的规则

Finding 是观察到的问题，RCA 是可审查诊断，ImprovementCandidate 仍只是 proposed。只有精确绑定的非自批 Approval 通过，promotion 才创建目标对象的新 accepted revision。

Finding→RootCauseAnalysis→ImprovementCandidate→Approval→Ledger revision
本课唯一胜利你能区分发现、诊断、建议和已生效变更四种状态，并证明模型或 proposer 不能自我晋升。
回忆学习链RCAPromotion实验

00 · RETRIEVAL FIRST

先区分证据、结论与变更

  1. REFUTES Evidence 与 VIOLATES Finding 各自表达什么？
  2. Finding 被 RCA 解释后，Finding 是否自动 closed？
  3. Approval RESOLVES 请求与 APPROVES 对象为何仍要分开？

本课只需记住

  • RCA 是规则驱动的 proposed 诊断，低置信度或高风险必须人工复核。
  • ImprovementCandidate 只 PROPOSES_CHANGE_TO，不代表目标已改变。
  • Promotion 需要精确 digest 绑定、非自批 approve 和正确 owning layer。

01 · FEEDBACK LIFECYCLE

每一层都保留自己的不确定性

Finding
observed failure
RCA
classified diagnosis
Candidate
proposed reusable change
Approval
independent decision
Revision
accepted fact

Finding DIAGNOSED_BY RCA；RCA PRODUCES ImprovementCandidate；Candidate PROPOSES_CHANGE_TO Evaluation、Knowledge 或 Engineering 层的拥有对象。Finding/Candidate 还可 TRIGGERS 新 ImpactSet，让规则变化重新进入影响分析，而不是直接修改生产事实。

为什么反馈闭环不能由模型端到端自动完成

模型可能帮助生成候选，但诊断分类、秘密检测、目标层所有权、Approval 绑定和 revision sealing 都是确定性边界。让同一 actor 提议并批准，会把一次错误输出永久写入系统规则。

02 · SOURCE READING 1

RCA 用确定性规则分类，并把不确定性显式带到记录中

Finding + FailureSignal → analyzeRootCause → proposed RCA

为什么读这段

诊断不是自由文本总结。responsible layer、category、confidence、verification 与 human review 都进入结构化内容。

packages/eval/src/feedback/rca.ts · analyzeRootCause 
const diagnosis = classify(spec.signal);
const content: RootCauseContent = {
  finding_id: spec.finding.id,
  observed_symptom: spec.finding.summary,
  evidence_ids: [...new Set(spec.signal.evidenceIds ?? [])].sort(),
  responsible_layer: diagnosis.layer,
  responsible_module: spec.signal.module ?? "unscoped",
  category: diagnosis.category,
  confidence: diagnosis.confidence,
  proposed_verification: diagnosis.verification,
  requires_human_review:
    diagnosis.confidence < HUMAN_REVIEW_CONFIDENCE || spec.signal.highRisk === true,
  rule: diagnosis.rule,
};
输入身份
RCA 绑定 Finding 和 evidence ids；重复 evidence 去重排序，保持 digest 稳定。
规则输出
分类器返回 layer、category、confidence 与建议验证，不让调用者任意组合。
不确定性
置信度低于阈值或 signal 为 high risk 时，requires_human_review=true。
生命周期
生成记录仍是 proposed；它解释 Finding，不自动关闭 Finding 或修改目标层。

03 · SOURCE READING 2

Promotion 同时阻止绑定漂移、自我批准和越层修改

Candidate + Request + Decision + Target → promoteImprovementCandidate → new revision

为什么读这段

真正写入事实层的函数必须重新验证 Approval 看见的 candidate digest，以及决定者和目标所有权。

packages/eval/src/feedback/promotion.ts · promotion guards 
if (
  input.request.object_id !== input.candidate.id ||
  input.request.object_digest !== input.candidate.digest ||
  input.decision.request_id !== input.request.request_id ||
  input.decision.object_digest !== input.candidate.digest
) {
  throw new FeedbackError(
    "promotion_binding_mismatch",
    `approval for improvement candidate ${input.candidate.id} does not bind its current digest`,
  );
}
if (input.decision.actor === proposedByOf(input.request)) {
  throw new FeedbackError(
    "self_promotion",
    `actor ${input.decision.actor} must not promote its own improvement candidate ${input.candidate.id}`,
  );
}
精确绑定
request 和 decision 都必须指向 candidate 当前 id/digest；旧版本批准不能追随新内容。
职责分离
decision actor 与 proposer 相同即 self_promotion，不看建议内容是否合理。
后续守卫
还要 decision=approve、target type 属于 candidate target layer，才能创建 revision+1。
写入结果
返回 accepted candidate 与 freshly digested target revision；调用方仍需通过 Ledger transaction 提交。
先判断：Approval 批准 candidate v1 后，模型补充说明生成 v2。能否用旧 decision 晋升 v2？应该触发哪个错误？

反馈生命周期

2. proposer 自己 approve 一个高质量候选，能晋升吗？

3. Finding 与 RCA 之间的关系是？

反馈晋升审查

  1. 画出 Finding → RCA → Candidate → Approval → Revision，并在箭头上写 relation。
  2. 列出 confidence、human review、digest binding、self-promotion、owning layer 五类守卫。
  3. 说明新 revision 何时才成为事实：promotion 返回时，还是 Ledger manifest 提交时。
