LESSON 0003 · CRITERION → VERDICT

一句验收条件，如何约束到最终 TaskVerdict

“需求里写过”不能证明任务完成。系统必须把每条已接受 Criterion 固定成稳定 Assertion，把它唯一分配给 Task，再用不可变 TDD contract 约束执行和证据。

全局系统→编译运行图→验收追踪→模型连通→治理与发布
本课唯一胜利你能从一个 Criterion 一路追到 TaskTddContract 和 Verdict，并指出“漏测、重复归属、执行时临时发明测试策略”分别在哪一层被阻断。

本课只需记住

  • 每条 accepted Criterion 确定性编译成 canonical Assertion。
  • Assertion 必须唯一归属 Task，模型只能建议分组。
  • TaskTddContract 固定策略与 digests，执行期不能临时改题。

01 · DESIGN PROBLEM

为什么 Criterion 不能直接挂到测试结果上？

自然语言需求会改写，任务会拆分，测试实现也会替换。若只靠字符串或名字关联，无法稳定回答“这条验收条件由哪个任务负责、用什么策略验证、证据是否属于同一语义版本”。

Criterion

PRD 中已接受的验收语义，拥有稳定 id、semantic digest 与 Test node 绑定。

Assertion

把验收语义物化成计划必须覆盖的可追踪声明；它保留 Criterion、Requirement、Test 与策略身份。

TaskTddContract

执行前编译出的不可变任务契约，规定哪些 assertion、测试策略和 TDD 阶段属于该 Task。

Evidence / Verdict

运行事实必须回指 contract 与 assertion；Verdict 只根据这条血缘裁决，不接受“测试绿了”的模糊声称。

02 · PRODUCTION CALL CHAIN

验收语义经过两次编译，才进入执行

Criterion
accepted semantic digest
Assertion
stable identity + coverage
TaskTddContract
unique owner + strategy
TDD Evidence
Red · Green · Refactor
TaskVerdict
passed or blocked

第一次编译把已接受 Criterion 变为 Assertion；planner 必须让每个 Criterion Assertion 恰好有一个 owner。第二次编译把已接受 DesignSet 中的测试策略与 Plan 中的 Task 固定为 contract。执行层只能履行 contract，不能临时改变适用范围。

两条核心不变量

完整覆盖：每条已接受 Criterion 恰好产生一个 Assertion。唯一归属：每个 Criterion Assertion 恰好由一个 Task 拥有。

04 · SOURCE READING 2

执行契约只能从已接受事实编译，不能由 planner 发明

调用链位置：final Plan + accepted DesignSet + PRD → compileTaskTddContracts → Task contracts

为什么读这段

它显示 strict TDD 是 CapabilityPlan 中的真实运行子图；只有子图存在才编译 contract，且输入缺失时 fail closed。

谁调用、输入是什么
Kernel coordinator 在进入严格执行前调用；上下文必须能提供 CapabilityPlan、final Plan、accepted DesignSet 与 accepted PRD。
第一个守卫
只有 Operation DAG 的 execute 节点明确带 strict_tdd subgraph 才进入编译；未激活时正常返回，不制造无关契约。
第二个守卫
紧随本切片的代码会检查 Plan、DesignSet、PRD；任一缺失抛出 binding_drift，而不是让 planner 补猜。
下游与证据边界
编译出的 contract 交给 strict TDD runner，runner 再要求 Red、Green、Refactor 血缘。这里证明契约来源，不单独证明 TaskVerdict 已通过。

本课结论

Assertion 固定“要证明什么”，TaskTddContract 固定“谁用什么策略证明”，TDD Evidence 记录“实际发生了什么”，Verdict 才回答“是否完成”。四者不能合并成一个测试结果字段。
