第 3 课 · 追踪主线

一条需求，什么时候才算真正兑现？

答案不是“代码写完了”，也不是“测试绿了”。你要能沿着 血缘 回到原子验收标准，证明它没有在设计、计划或 TDD 执行中被换掉。

本课的唯一胜利

选一条 Criterion，从源头追到 Verdict，并指出任一绑定断裂时系统最早在哪一层拒绝继续。

PrdProposal → Requirement + atomic Criterion → Test seed → canonical Assertion → DesignSet.test_strategy → final CapabilityPlan → PlanProposal → ExecutionPlan + Task → TaskTddContract → Baseline → Red → Green → Refactor → Evidence → TaskVerdict → Snapshot

Screen 3 · Code ↔ 中文

Assertion 不由 Planner 自由发明

规范化（canonical） Assertion 是 Criterion 的可执行验收身份。下面 9 行是当前仓库原样摘录；它的重点不是 TypeScript 语法，而是“每条 Criterion 都通过同一公式获得身份”。

这段代码在说
  1. criteria.map：输入有几条原子 Criterion，就逐条编译，不把两条悄悄合并。
  2. primary_strategies：如果设计治理已给 Criterion/Test 对指定主策略，把它带上；没有就不伪造。
  3. criterionAssertionId：身份只由 Criterion id 与语义 digest 按固定公式生成。
Aha

无关 Criterion 被插入时，旧 Assertion 的身份应保持稳定；某条 Criterion 语义变了，只旋转它对应的身份。这让审计者能分清“新增”与“偷换”。

Screen 4 · 决策练习

四条绑定断了，最早应该在哪里停？

fail closed 的要点是“在最早能确定不可证明的地方停下”。先口头作答，再展开对照。

01 Criterion → Test seed 绑定断裂
最早停在：TaskTddContract 编译层

Kernel 从 Task Assertion 取 Test id 后找不到已接受的 Criterion lineage，抛出 binding_drift；不得进入 TDD 执行。

证据：kernel-coordinator.ts:2479–2496
02 Assertion → Task 归属断裂
最早停在：Plan 覆盖校验层

每个 criterion_assertion 必须恰有一个拥有者。零个或多个 Task 都是计划无效，不应等到测试或 Verdict 再发现。

证据：assertions.ts:100–116
03 DesignSet → TddContract 绑定断裂
最早停在：合同编译／校验层

找不到 primary test strategy，或合同绑定的 Plan/CapabilityPlan 已过期，均抛出 binding_drift；Planner 不能自行补一个策略。

证据：kernel-coordinator.ts:2498–2519
04 Red Evidence → production grant 绑定断裂
最早停在：Strict TDD 权限发放层

语法错误、超时、无结构结果或未命中目标 Assertion 都不形成 Red Evidence。没有被接受的 Red digest，就不发放生产写入 grant。

证据：execution-runner.ts:200–205
再做一步：不只说“不行”

选一张卡，用这个句式回答：“我在 层 拒绝，因为缺少 绑定；若继续，将无法证明 业务声称。”

Screen 6 · 闭卷检索

不回看：你能从现象定位裁决层吗？

这 3 题检查的不是名词记忆，而是你能否用 TaskVerdict 的证据逻辑拒绝一个过早的“已完成”。

01

某条 Criterion 的语义 digest 发生变化，另一条无关 Criterion 未变。正确的 Assertion 身份结果是？

02

某 Assertion 有可运行的 Test，但在 ExecutionPlan 中没有任何 Task 拥有它。系统应该？

03

Red 阶段只产生了语法错误，但 Agent 声称实现已准备好。下一步应该？

课后完成标准

  • 不看页面，口述 Criterion → Assertion → Task → TaskTddContract → Evidence → Verdict。
  • 能解释“测试通过”为什么仍可能不足以完成 Task。
  • 选一条真实 Criterion，记录其追踪结果与残余不确定性。
