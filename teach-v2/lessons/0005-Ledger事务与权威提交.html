LESSON 0005 · TRANSACTION → MANIFEST → REPLAY

文件已经写入，为什么还不算系统事实

Ledger 的难点不是把 JSON 写到磁盘，而是让并发、崩溃和重试之后仍只有一条可验证历史。权威边界在提交清单，不在 staging、日志或 SQLite。

意图与设计→编译运行图→受控执行→Ledger 提交→重放与投影
本课唯一胜利你能解释 Transaction、shard、manifest 与 replay 的职责，并判断一次中途崩溃留下的文件为什么不能冒充已提交事实。

01 · GLOBAL POSITION

提交协议把“产生结果”变成“接受事实”

TransactionInput
artifacts + edges + events
Staging
先写隔离区
Validate
schema + sequence + baseline
Publish shards
内容就位但尚未授权
Publish manifest
提交点与重放入口

Repository 同时解决三类竞争：同一 operation 的幂等重试、等待锁期间的另一写者、以及 baseline 漂移。失败时保留或清理的文件属于恢复材料；只有 manifest 使它们成为 committed operation。

进阶：为什么不用“把目录 rename 一次”当原子提交？

事务跨 artifacts、edge shard、event shard 与 manifest 多个路径，还要验证仓库基线和序号。设计采用“内容先发布，manifest 最后发布”的协议；重放者以 manifest 为准，因此中间态不会进入权威读取。

02 · SOURCE READING 1

append-only 不是口号，而是 operation id 与 sequence 的双重守卫

调用链位置：已提交 manifests + candidate → assertAppendOnly → sequence acceptance

为什么读这段

它定义“下一条历史”的唯一合法位置，并把重复 operation 与序号分叉变成不同的类型化失败。

packages/core/src/ledger/event-store.ts · assertAppendOnly 
export function assertAppendOnly(
  operations: readonly CommittedOperation[],
  candidate: { readonly ledger_operation_id: string; readonly sequence: number },
): void {
  if (operations.some((op) => op.manifest.ledger_operation_id === candidate.ledger_operation_id)) {
    throw new LedgerConflict(
      `ledger operation is already committed: ${candidate.ledger_operation_id}`,
    );
  }
  const expected = nextSequence(operations);
  if (candidate.sequence !== expected) {
    throw new LedgerSequenceError(
      `append-only violation: next sequence is ${expected}, got ${candidate.sequence}`,
    );
  }
}
谁调用
LedgerRepository.commit 在锁内重新读取已提交 operations 后调用。
两个守卫
operation id 防止同一业务提交被重复接受；连续 sequence 防止历史出现空洞或分叉。
为什么在锁内
锁外检查只能优化幂等重试；等待锁期间历史可能变化，因此裁决必须基于锁内新读的状态。
证据边界
函数单测能证明局部规则，不能证明完整提交顺序或崩溃边界。

03 · SOURCE READING 2

manifest 是最后写入的提交点

调用链位置：validated staging → shards → manifest → committed result

为什么读这段

这几行决定崩溃边界：shards 即使已经 rename，只要 manifest 未发布，重放就不会把它们视为已提交 operation。

packages/core/src/ledger/repository.ts · commit publish phase 
await this.publishShards(context);
this.atBoundary("shards.renamed", context);

const manifest = buildManifest({
  ledger_operation_id: input.ledger_operation_id,
  workflow_operation_id: input.workflow_operation_id,
  attempt_id: input.attempt_id,
  baseline_commit: input.expected_baseline,
  sequence,
  artifact_digests: [...digests.artifactDigests],
  edge_file: context.edgeFile,
  event_file: context.eventFile,
  edge_file_digest: digests.edgeFileDigest,
  event_file_digest: digests.eventFileDigest,
  ...requiredReaderVersionField(input.required_reader_version),
  committed_at: this.now(),
});
this.publishManifest(manifest, context);
顺序不变量
shards 先就位，manifest 后授权；读取者不会看到 manifest 指向尚未就位的内容。
绑定内容
manifest 固定 baseline、sequence、artifact 与 shard digest，以及所需 reader version。
失败语义
在 shards.renamed 后崩溃会留下孤儿 shard，但没有 manifest 就不是 committed history。
下游
readCommittedOperations 与 replay 从 manifests 建立权威集合，materializer 只投影该集合。
迁移判断：若 manifest 已提交但 SQLite 尚未刷新，正确修复是重写 Ledger，还是从 Ledger 重建投影？答案必须引用权威方向。
